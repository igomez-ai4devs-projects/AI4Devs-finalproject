# [C1] T-C1-01 · Scaffold the six `incident` libraries with their three-axis tags

## Context

Foundation work with no user story behind it. Sources: `docs/product/ARCHITECTURE.md` §5.1, which lists exactly six libraries for the `incident` context, and §5.5, which gives the generator invocations with their tags; and `docs/backlog/epic-map.md` → section **`C1` · Incident Management**, *What actually remains*, which opens with *"Everything. Six libraries in the `incident` context (`domain`, `application`, `infrastructure`, `feature`, `ui`, `data-access`)"*. `docs/backlog/C1/user-stories.md` § *Scope boundary* records the same ownership. The Business Analyst correctly wrote no story: scaffolding has no persona and no user-observable behavior.

**Not priced here.** The Nx workspace, pnpm, the ESLint flat config with `@nx/enforce-module-boundaries`, the tag scheme, the four applications, `libs/shared/{contracts,domain,ui,util}` and the base migration chain are **priced once into `C10`** (epic map, *Foundation ownership*) and already ticketed at `T-C10-01` → `T-C10-17`. This ticket assumes all of it exists.

The six libraries span both platforms, so the work belongs to neither dev agent alone; it sits at the **workspace scaffolding** layer on the **shared platform**, hence `agent: —`.

**Known gap, not this ticket's to close.** No `C1` ticket currently brings the first component or spec into `libs/incident/ui` (`T-C1-10` and `T-C1-101` explicitly build the intake/detail screens with hand-written semantic HTML instead, deferring the design system). `libs/incident/ui/jest.config.ts` therefore keeps `passWithNoTests: true` with no ticket that retires it. Flagged here for whichever ticket eventually lands `incident-ui`'s first component to pick up; out of scope for this ticket to invent.

## Scope

- Generate exactly six libraries with the tags of `ARCHITECTURE.md` §5.5:
  - `libs/incident/domain` — `platform:backend,scope:incident,type:domain`
  - `libs/incident/application` — `platform:backend,scope:incident,type:application`
  - `libs/incident/infrastructure` — `platform:backend,scope:incident,type:infrastructure`
  - `libs/incident/feature` — `platform:frontend,scope:incident,type:feature`
  - `libs/incident/ui` — `platform:frontend,scope:incident,type:ui`
  - `libs/incident/data-access` — `platform:frontend,scope:incident,type:data-access`
- Barrel `index.ts` per library; Jest configured per library; path aliases registered in `tsconfig.base.json`.
- Out of scope: any aggregate, port, use case, entity, component or migration. Also out of scope: the `apps/api` module wiring and the `incident` schema namespace (`T-C1-02`).

## Acceptance criteria

Mechanical checks — this ticket has no user scenario.

**Given** the workspace **When** the projects are listed **Then** exactly those six exist under `libs/incident/`, and no seventh project exists there.

**Given** each project **When** its tags are inspected **Then** it carries exactly three tags matching the list above, with no fourth tag and no missing axis.

**Given** a probe import of `libs/incident/infrastructure` from `libs/incident/domain` **When** `pnpm nx lint incident-domain` runs **Then** it fails on the `type:` constraint matrix of `ARCHITECTURE.md` §5.3; the probe is reverted before the ticket is closed.

**Given** a probe import added to `libs/incident/domain`, of a temporary project tagged `platform:backend,scope:sla,type:domain` — standing in for `libs/sla/domain`, which does not exist yet (SLA is scaffolded by its own epic); same platform and a legal `type:` for `domain` to depend on, only the scope is illegal — **When** lint runs **Then** it fails on the `scope:` rule — the isolation `ARCHITECTURE.md` §8 requires and `US-C1-17` depends on; both the import and the temporary project are removed before the ticket is closed.

**Given** a probe import added to `libs/incident/application`, of a temporary project tagged `platform:frontend,scope:incident,type:util` — same scope, and `util` is a `type:` `application` may legally depend on; only the platform is illegal — **When** lint runs **Then** it fails on the `platform:` rule. (A probe importing `libs/incident/feature` directly does not isolate this: `type:application` may not depend on `type:feature` either, and `@nx/eslint-plugin`'s `enforce-module-boundaries` rule reports only the first `depConstraints` entry it matches — the type-matrix family, checked before platform in `eslint.config.mjs` — so the platform message would never appear.) Both the import and the temporary project are removed before the ticket is closed.

**Given** the workspace **When** `pnpm nx run-many -t lint test` runs **Then** all six projects pass, and `pnpm nx graph --file=tmp/graph.json` shows no edge the §5.3 matrix forbids.
