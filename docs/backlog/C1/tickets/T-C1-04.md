# [C1] T-C1-04 · Reference-number sequence, immutability trigger, adapter and concurrency proof

## Context

`US-C1-05` requires that two Incidents created concurrently never share a reference, and that uniqueness is guaranteed **by a database constraint, not by an application-level check a race can defeat**. It further requires that a reference is never modified and never re-issued — including when an Incident is cancelled or deleted (`NFR-DAT-01`).

**Narrowed this pass.** This ticket no longer adds the `reference` column: `T-C1-06` (the table-creating migration) now carries `reference varchar(20) NOT NULL` and `uq_incident_reference` in the same migration as the rest of the first `DATA-MODEL.md` §8.5 column group, because a table-creating migration that omits the reference `NOT NULL` column would leave `T-C1-06`'s own "every field round-trips" acceptance criterion unprovable and could persist a referenceless row.

**Finding closed this second pass (was open) — `DATA-MODEL.md` §3.2/§3.7, decision M18.** The architect has decided the immutability mechanism: a **column-immutability guard trigger**, the one trigger category §3.7 sanctions. `REVOKE UPDATE (reference)` was rejected because a column-level `REVOKE` has no effect while the role still holds table-level `UPDATE`, and — decisively — every environment that exists today (`docker/docker-compose.dev.yml`, `docker/docker-compose.e2e.yml`) connects as `postgres`, which no `REVOKE` binds. This ticket's migration therefore creates, in the `incident` schema:
- `incident.incident_reference_seq`, declared **`NO CYCLE`** explicitly (never reused, §3.2).
- `incident.fn_reject_reference_update()`, a `plpgsql` function that raises on any attempted change.
- `tg_incident_ticket_reference_immutable`, a `BEFORE UPDATE OF reference ON incident.incident_ticket … WHEN (OLD.reference IS DISTINCT FROM NEW.reference)` trigger calling that function — fires for every role, the owner and a superuser included, writes nothing, reads nothing but the row, and encodes no policy (the exact §3.7 test).

The `down` migration drops the trigger and the function, in that order, then the sequence — no residual object survives a revert.

**Order finding closed this second pass — `T-C1-06` still runs before `T-C1-04`, and that stays safe.** A parallel finding asked whether `T-C1-06`'s own round-trip acceptance criterion (save an aggregate, reload it) writes a row before this ticket's trigger exists, which would appear to contradict `DATA-MODEL.md` §8.5's "no row may ever exist without a reference" framing. It does not conflict, for two independent reasons, both recorded here so the reasoning is not silently lost: (1) `T-C1-06`'s own test performs an **`INSERT` and a `SELECT` only** — it never issues an `UPDATE` of `reference` — so the one thing this ticket's trigger guards against is never exercised by `T-C1-06`'s own acceptance criterion; (2) the object this ticket's trigger and sequence must genuinely precede is the **first production-reachable write path**, `T-C1-07`'s `LogIncidentUseCase`, not a ticket's own internal test harness — and that path already sits *after* this ticket in the build order (`03 → 05 → 06 → 04 → 07`). `CREATE TRIGGER … ON incident.incident_ticket` also cannot run before the table exists, which rules out moving this ticket ahead of `T-C1-06` — the two migrations are correctly ordered as they stand. No ticket file order changes because of this finding; see the C1 README's finding **H2** for the restated justification.

## Scope

- Migration, run after `T-C1-06`'s table-creating migration, adding: `incident.incident_reference_seq` (`NO CYCLE`), `incident.fn_reject_reference_update()` and `tg_incident_ticket_reference_immutable` on `incident.incident_ticket`, inside the `incident` schema namespace from `T-C1-02`.
- Adapter implementation of `nextReference()` allocating from that sequence within the caller transaction.
- Reversible `down` migration dropping the trigger, the function and the sequence, per the convention fixed by `T-C10-17`.
- Out of scope: the aggregate (`T-C1-05`); the `reference` column itself and `uq_incident_reference`, both created by `T-C1-06`'s table-creating migration; the mapper's `update: false` mapping for `reference`, which is `T-C1-06`'s own defence-in-depth addition alongside the column it owns.

## Acceptance criteria

**Given** two Incidents created concurrently in separate transactions **When** both commit **Then** their references differ, and the guarantee still holds with the application-level check removed, proving the constraint and not the code enforces it.

**Given** an existing, persisted Incident **When** a direct SQL `UPDATE` changes its `reference`, run **as the `postgres` role** (the role every current environment connects as) **Then** the write is rejected by the trigger, not by an application-level guard.

**Given** an Incident that is cancelled and one that is deleted **When** the next reference is allocated **Then** it is a new value; neither released number is ever re-issued.

**Given** the migration **When** it is run, reverted and run again **Then** the outcome is identical each time and no residual object remains after the revert.
