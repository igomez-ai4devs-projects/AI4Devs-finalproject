# [C1] T-C1-06 · TypeORM `Incident` entity, mapper, repository adapter and migration

## Context

`US-C1-01` needs the aggregate of `T-C1-05` to survive a restart. ADR-005 requires persistence entities to be **separate from domain aggregates**, joined by an explicit mapper, so the schema can evolve without deforming the model.

The migration chain, the data source and the `synchronize: false` rule come from `C10` (`T-C10-16`, `T-C10-17`); the `incident` schema namespace comes from `T-C1-02`.

**Narrowed by ADR-014 / `DATA-MODEL.md` §8.5.** `incident_ticket`'s dictionary shape (§20.3) is the **target**, not what this migration creates: a column is introduced by the migration of the first behavior that writes it, and this ticket is the table-creating migration for the logging behavior only (`FR-INC-01`/`02`) — the first row of §8.5's introduction table. Every later column group — `logged_by_user_id` (`T-C1-11`), `category_id` (`T-C1-21`), the assessment and matrix columns (`T-C1-30`), the competition flag columns (`T-C1-43`), the lifecycle columns (`T-C1-50`) — arrives with its own migration and is explicitly **out of scope here**, including the four priority `CHECK` constraints and `ck_incident_resolution` / `ck_incident_triaged_beyond_new`, which cannot exist before the columns they reference do.

**`reference` moves here from `T-C1-04`.** `T-C1-04` no longer creates the Incident table (it never did — this ticket does) and now no longer adds a column to it either: without `reference` on this migration, "every field round-trips" (this ticket's own first AC) is unprovable and this table-creating migration would leave rows with no reference at all, contradicting `US-C1-05`'s "every Incident has a reference from the moment it exists." `T-C1-04` keeps the sequence, the immutability trigger, the `nextReference()` adapter and the concurrency proof; it runs after this ticket and adds no column, only `uq_incident_reference`'s supporting sequence and trigger on the column this ticket already created. The build order is unchanged: `T-C1-03 → T-C1-05 → T-C1-06 → T-C1-04` (finding H2, README).

**Defence in depth for immutability (M18).** `T-C1-04`'s trigger is the database-level guarantee; this ticket's entity maps `reference` with **`update: false`**, so TypeORM never emits it in an `UPDATE` statement for any writer that goes through this repository. That is a second, independent layer — not the guarantee itself, which stays the trigger's job, and not a substitute for it: a raw SQL statement or a defective adapter would still need the trigger to be stopped.

**Closed this pass — `T-C1-06`'s own write does not need `T-C1-04`'s trigger to exist first.** This ticket's own round-trip acceptance criterion performs an `INSERT` and a `SELECT`, never an `UPDATE` of `reference`, so it does not exercise the one thing `T-C1-04`'s trigger guards against. The trigger only has to exist before the first **production-reachable** write path — `T-C1-07`'s `LogIncidentUseCase` — and it already does, since `T-C1-04` sits between this ticket and `T-C1-07` in the build order. See `T-C1-04`'s own `## Context` for the full reasoning; no ticket order changes because of this.

**No entity has ever been registered in this codebase before this ticket.** `T-C1-02` registered only "the `incident` TypeORM entity path in the data source, with no entity yet declared" — this is the first real entity class in `apps/api`. **Flagged, not resolved:** `docker/backend/Dockerfile` copies only `dist/apps/api` (webpack's single `main.js` bundle plus the generated `package.json`, per `T-C10-69`'s own finding on the same image). If the data source registers entities by a glob path (`__dirname + '/**/*.entity.js'` or similar) rather than an explicit class import, that pattern resolves against files on disk that do not exist inside a single bundled `main.js` — the entity would silently be absent from the running image even though it compiles and its unit/integration tests pass locally against `ts-node`. Whether the fix is an explicit entity array, a webpack `externals`/copy step, or a different registration strategy is a packaging decision for `ci-cd-expert`, not made here; this ticket only names the risk so it is verified against the actual deployed image before this becomes the pattern six more entities repeat.

## Scope

- TypeORM entity for `incident.incident_ticket` in the `incident` schema, with UTC timestamp columns, carrying **exactly** the first column group of `DATA-MODEL.md` §8.5's introduction table: `id`, `reference varchar(20) NOT NULL` (+ `uq_incident_reference`, mapped **`update: false`** — defence in depth for M18, alongside `T-C1-04`'s trigger), `short_description`, `description`, `origin_channel`, `reporter_user_id`, `service_id` (nullable), `created_at`, `updated_at`, `created_by`, `updated_by`, `version`. No `workflow_id`, `state_id`, `state_category`, `priority_matrix_id`, `category_id`, `logged_by_user_id`, any assessment column or the competition flag exists yet.
- `incident.origin_channel_enum` created with **exactly** `portal`, `agent_logged`, `email`, `in_app` — **not** `phone` (Product Owner decision, being written into the PRD in parallel with this pass; matches the closed set `libs/incident/domain`'s `OriginChannel` value object already enforces).
- Bidirectional mapper between entity and `Incident` aggregate, with round-trip tests. `created_at` / `created_by` are read from and written to the aggregate's `loggedAtEpochMs` / `loggedBy`, not from a separate persistence-only clock read (ADR-014 rule 4: persistence never invents domain state).
- **The mapper's side of ADR-014's rule 4.** The aggregate slots this ticket's table has no column for yet — `categoryId`, `impact`, `urgency`, `priority`, `competitionAffectsInProgress`, `affectedSubject`, `assignment` — are read back from the row as `null` / `false` on load. On save, the mapper **refuses** with a typed mapping error if any of those slots is not empty (non-`null`, non-`false`) — never a silent drop of a value the aggregate actually carries.
- `TypeOrmIncidentRepository` implementing `IncidentRepositoryPort`, bound to its token in `IncidentModule`.
- Migration creating the table.
- Out of scope: every column introduced by a later block — `logged_by_user_id` (`T-C1-11`), `category_id` (`T-C1-21`), assessment and matrix columns (`T-C1-30`), the competition flag (`T-C1-43`), lifecycle (`T-C1-50`), links, entries and assignment — each arrives with its own migration and its own mapper extension.

## Acceptance criteria

**Given** an aggregate saved through the repository **When** it is loaded again **Then** every field round-trips unchanged, asserted against a real PostgreSQL instance rather than a mock.

**Given** a newly logged Incident **When** it is saved and reloaded **Then** it has a `null` category, Impact, Urgency and Priority, the competition-in-progress flag reads `false`, and no lifecycle column exists to be written — the shape ADR-014 and `DATA-MODEL.md` §8.5 declare for a just-logged Incident, not a triaged one.

**Given** the entity **When** the domain library is inspected **Then** no TypeORM decorator and no entity type appears in `libs/incident/domain`; the mapper is the only object that knows both.

**Given** the data source **When** the application boots in any environment **Then** `synchronize` is `false`, and migrations auto-run only when `NODE_ENV=development`.

**Given** the migration **When** it is run and reverted **Then** it succeeds both ways and leaves no residual object.
