# [C1] T-C1-09 · `incident/data-access` — Incident API service and signal store

## Context

`US-C1-01` and every later frontend ticket in this epic read and write Incidents through one place. `ARCHITECTURE.md` §7.1 puts `HttpClient` access and signal state in the context `type:data-access` library; the `type:ui` libraries must never inject a service or `HttpClient`.

The JWT and locale interceptors are `apps/web` concerns already delivered by `C10` (`T-C10-30`) — **except that this delivery slice ships with no authentication at all**, per the Product Owner's minimal cut (`T-C10-74`); this ticket calls the API exactly as it would once auth lands, so nothing here changes when it does.

**Widened by 0.5h — the "see it" half of `US-C1-01`.** As first written, this ticket covered intake only. Delivery slice 1 also needs `GetIncidentByReference` (`T-C1-99`/`T-C1-100`) called from somewhere, and this is that place: one service, one store, both halves of the same resource.

## Scope

- `IncidentApiService` in `libs/incident/data-access` using `HttpClient` and the typed DTOs from `libs/shared/contracts`, covering both the intake `POST` and the detail `GET /incidents/{reference}` (`T-C1-100`).
- A signals-based store exposing loading, error and data as separate, always-defined states — no swallowed HTTP error and no undefined loading state — for both calls.
- `computed()` selectors for the views built in later tickets; `effect()` used sparingly or not at all.
- Out of scope: any component; any derivation of Priority or of any other server-owned value (`T-C1-31`).

## Acceptance criteria

**Given** a successful intake call **When** the store settles **Then** the data signal holds the typed response, loading is false and error is null.

**Given** a failing intake call **When** the store settles **Then** the error signal holds a typed error, loading is false, and the failure is never silently discarded.

**Given** the data-access library **When** lint runs **Then** it depends only on `type:data-access`, `type:contracts` and `type:util` projects, per the §5.3 matrix.

**Given** the store **When** it is unit-tested with `jest-preset-angular` **Then** the three states are asserted without a running API, for both the intake call and the detail-by-reference call.

**Given** a call to `GET /incidents/{reference}` **When** the store settles **Then** the same three-state contract applies — loading, error and data are never undefined at once, and a `404` populates the error signal rather than throwing past the component.
