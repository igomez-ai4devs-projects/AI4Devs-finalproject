# [C1] T-C1-100 · `GET /incidents/{reference}` route and its response contract

## Context

The HTTP half of `T-C1-99`. "See it" is a redirect target from the `201` of `T-C1-08`'s intake response, landing on this route by reference — never an echo of what was posted.

**Deferred, by the user's explicit decision this pass:** field-level i18n. Response strings that reach the client (the not-found message included) are sourced from a per-feature constants file (see `T-C1-101`'s note), not `nestjs-i18n`, matching the same debt this delivery slice accepts across `T-C1-08` and `T-C1-10`.

## Scope

`T-C1-99` is built. This ticket wires the HTTP adapter around what actually exists: `GetIncidentByReferenceUseCase.execute(reference: TicketReference)`, depending only on `IncidentReadRepositoryPort`, returning `Result<IncidentSnapshot, IncidentNotFoundOutcome>`.

- `IncidentDetailResponse` **type** in `libs/shared/contracts` (ADR-007, types only): the read-shaped projection of `IncidentSnapshot`. **Excludes `IncidentSnapshot.id`** — the internal UUID v7 is a storage detail the requester is never given a reason to see (AC3/AC4 below); every other snapshot field maps across directly, keyed on `reference`, not `id`.
- A `class-validator`-decorated params DTO for the `:reference` path segment (e.g. `GetIncidentByReferenceParamsDto`), matching `TicketReference`'s own shape — `^[A-Z]{3}[0-9]{7}$` (`libs/shared/domain/src/lib/ticket-reference.vo.ts`). Validated by the **already-configured** global `ValidationPipe` (`apps/api/src/main.ts`: `whitelist`, `forbidNonWhitelisted`, `transform`, `stopAtFirstError`, `exceptionFactory` → `RequestValidationException`) — the same mechanism `T-C1-08`'s body DTOs already use, not a bespoke validation path for this one route.
- `IncidentController` GET route in `apps/api`:
  - Accepts the path parameter only through the DTO above; constructs `TicketReference.fromString()` only once that DTO has already proven the shape, so a malformed reference never reaches the use case.
  - Calls `GetIncidentByReferenceUseCase.execute(reference)`. On the `ok` branch, maps `IncidentSnapshot` to `IncidentDetailResponse` and returns `200`. On the `err` branch (`INCIDENT_NOT_FOUND`), throws Nest's own `NotFoundException` — see "Resolved" below for why no new filter code is needed for this to become a contract-shaped `404`.
  - Resolves and echoes the correlation id the same way `IncidentController.logIncidentAsRequester` already does (`resolveCorrelationId`, `CORRELATION_ID_HEADER` response header, `T-C1-08`) — this route is not a special case.
  - No `Location` header — unaffected; this route is the *target* a future `Location` would point to, not a new source of one.
- `IncidentModule` wiring: binds the **same** `TypeOrmIncidentRepository` instance to both `INCIDENT_REPOSITORY` and `INCIDENT_READ_REPOSITORY` — e.g. one provider `{ provide: INCIDENT_REPOSITORY, useClass: TypeOrmIncidentRepository }` and a second `{ provide: INCIDENT_READ_REPOSITORY, useExisting: INCIDENT_REPOSITORY }`. One adapter, two ports, never two instances (`T-C1-99`'s closing note).
- Out of scope: the use case (`T-C1-99`); the client component (`T-C1-101`); any new exception filter — none is needed, see below.

## Resolved — the exception-filter dependency this ticket previously flagged

**No longer a gap; nothing here waits on `T-C10-40`.** `T-C1-08` did not wait for it either: it already built `GlobalExceptionFilter` (`apps/api/src/app/global-exception.filter.ts`), registered globally in `main.ts`, as the minimum that ticket owed ahead of `T-C10-40`'s eventual, richer replacement. That filter **already** recognizes `NotFoundException` and maps it to `404` / `{ error: { code: ErrorCode.NOT_FOUND } }`, and **already** recognizes `RequestValidationException` and maps it to `400` / `{ error: { code: ErrorCode.VALIDATION_FAILED, details } }`. This ticket needs neither a new filter nor a new mapping — only to throw the exception type each case already calls for (Scope above).

The `400`/`404` split is deliberate, not a coin flip: `ErrorCode.VALIDATION_FAILED` is documented as "the request body **or parameters** failed validation" — a reference that does not even match `TicketReference`'s shape is a malformed parameter, the same category as any other bad input `T-C1-08` already rejects at `400`. `ErrorCode.NOT_FOUND` is documented as "the requested resource does not exist" — reserved for a syntactically valid reference with no matching row. Collapsing both into `404` would make `VALIDATION_FAILED` meaningless for this route and would tell a client with a typo'd reference that nothing is wrong with what they sent.

## Acceptance criteria

**Given** an existing Incident's reference **When** the route is called **Then** it responds `200` with the full persisted state — never the request body echoed back.

**Given** a reference that is syntactically well-formed (matches `TicketReference`'s shape) but matches no Incident **When** the route is called **Then** it responds `404` with `{ error: { code: 'NOT_FOUND' } }`.

**Given** a path parameter that does not match `TicketReference`'s shape (wrong length, lowercase letters, wrong prefix format) **When** the route is called **Then** it responds `400` with `{ error: { code: 'VALIDATION_FAILED', details: [...] } }` naming the `reference` parameter, and the request never reaches `GetIncidentByReferenceUseCase`.

**Given** the response body **When** it is inspected **Then** it contains no field the requester is not permitted to see and no internal identifier that leaks storage details unrelated to the reference itself — in particular, `IncidentSnapshot.id` never appears in `IncidentDetailResponse`.

**Given** the contracts library **When** it is inspected **Then** `IncidentDetailResponse` carries no `class-validator` decorator — it is a type only, per ADR-007.

**Given** `IncidentModule` **When** it is inspected **Then** `INCIDENT_REPOSITORY` and `INCIDENT_READ_REPOSITORY` resolve to the same `TypeOrmIncidentRepository` instance, never two separate instances.
