# [C1] T-C1-100 · `GET /incidents/{reference}` route and its response contract

## Context

The HTTP half of `T-C1-99`. "See it" is a redirect target from the `201` of `T-C1-08`'s intake response, landing on this route by reference — never an echo of what was posted.

**Deferred, by the user's explicit decision this pass:** field-level i18n. Response strings that reach the client (the not-found message included) are sourced from a per-feature constants file (see `T-C1-101`'s note), not `nestjs-i18n`, matching the same debt this delivery slice accepts across `T-C1-08` and `T-C1-10`.

## Scope

- `IncidentDetailResponse` **type** in `libs/shared/contracts` (ADR-007, types only): the full Incident state `T-C1-99` returns, shaped for read, never for write.
- `IncidentController` GET route in `apps/api` mapping the path parameter to `GetIncidentByReferenceUseCase`, returning `200` with the typed body or `404` on the not-found outcome.
- No new exception-filter mapping introduced here — this route reuses whatever mapping already exists for the not-found case by the time it is implemented; **this ticket does not build an exception filter**, see the finding below.
- Out of scope: the use case (`T-C1-99`); the client component (`T-C1-101`).

## Acceptance criteria

**Given** an existing Incident's reference **When** the route is called **Then** it responds `200` with the full persisted state — never the request body echoed back.

**Given** a reference that matches no Incident **When** the route is called **Then** it responds `404` with a machine-readable error code, not a generic failure.

**Given** the response body **When** it is inspected **Then** it contains no field the requester is not permitted to see and no internal identifier that leaks storage details unrelated to the reference itself.

**Given** the contracts library **When** it is inspected **Then** `IncidentDetailResponse` carries no `class-validator` decorator — it is a type only, per ADR-007.

## Reported, not resolved — dependency gap found while writing this ticket

`T-C1-08`'s own `## Scope` says its domain-error-to-contract-error-code mapping is done "by the exception filter established in `T-C10-40`." `T-C10-40` (`C10` block C, RBAC) is **not** part of this narrowed delivery slice. This ticket's `404` mapping needs *some* exception filter to exist; whether that is `T-C10-40` arriving after all, a smaller stand-in scoped to this slice, or a decision that `T-C1-08` and this ticket share a lighter mechanism for now is a call this ticket does not make. Flagged for the Product Owner / Architect rather than guessed at here.
