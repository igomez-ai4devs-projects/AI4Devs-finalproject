# [C1] T-C1-102 · Untriaged-period configuration and the "overdue for triage" indicator

## Context

**New this pass.** `docs/product/PRD.md` §14.10 (D2) and the new `FR-INC-20` require that an Incident MUST NOT remain in `New` without a category indefinitely: the system must apply a **configurable maximum untriaged period** to every Incident in `New`, and an Incident that exceeds it without a category must become visibly **overdue for triage**. `DATA-MODEL.md` §8.5 is explicit that nothing new is persisted for this: an Incident is overdue when `state_category = 'new'`, `category_id IS NULL` and its time in `New` (`created_at`, repeated as `occurred_at` on its creation `incident_state_transition` row) exceeds the configured maximum — every input already exists once `T-C1-50` lands. `ix_incident_untriaged` (`(created_at)` partial `WHERE state_category = 'new'`, `DATA-MODEL.md` §16) is created by `T-C1-50` for exactly this query.

**Reparented this pass (F32).** `docs/backlog/C1/user-stories.md` has been regenerated and now carries `US-C1-34` ("An Incident overdue for triage becomes visible to the Service Desk"), authored directly against `FR-INC-20`, exactly as this ticket's own finding asked. `story: —` is retired in favor of `US-C1-34`; this ticket's scope, acceptance criteria and dependency on PRD assumption A11 are unchanged by the reparenting — only the traceability field moves. `FR-INC-19` was resolved separately, as its own story `US-C1-33`, not folded into `US-C1-07`/`US-C1-15`/`US-C1-24` (see those stories' own findings and `T-C1-49`/`50`/`51`/`73`'s `## Context`).

**Dependent on PRD assumption A11 — deliberately, no value invented.** `FR-INC-20` states plainly that "the period value and the default action on expiry are open points (§10 A11, §14.10)" and A11 itself: "the service organization will set the maximum untriaged period... This PRD deliberately states no value: none has been given by the business." This ticket does not guess one. It follows the same pattern already established for the Priority matrix (`T-C1-27`) and auto-close (`T-C1-63`): the period is validated configuration through `ConfigService`, with **no in-code default** — the application fails fast at boot if the key is absent, exactly as it already does for a missing matrix or a missing confirmation period. What is undecided is the number an operator eventually sets and what happens beyond visibility (a reminder or an escalation, `FR-INC-13`) — both are `FR-WFL-05` time-based rules configured through `incident_business_rule` rows with `event = 'scheduled'` (`DATA-MODEL.md` §8.4/§8.5/§20.3), a `C12` mechanism this ticket calls, not rebuilds.

**Sequencing.** This ticket needs `state_category = 'new'` (`T-C1-50`) and `ix_incident_untriaged` (also `T-C1-50`), so it ships after block F, not with block B or C despite reading `category_id` (`T-C1-21`) as well.

## Scope

- Untriaged-period key in validated configuration (`ConfigService`), with **no code-level default**; boot fails fast naming the missing key if it is absent, zero, negative or not a duration — the same pattern as `T-C1-27`'s matrix and `T-C1-63`'s confirmation period.
- A query/read model (`IsOverdueForTriage` or equivalent) evaluating, for an Incident in `New`, `state_category = 'new' AND category_id IS NULL AND now() - created_at > configured_period`, executed against `ix_incident_untriaged` — no new column and no stored flag (`DATA-MODEL.md` §8.5 explicitly rejects a persisted `triage_overdue`/`triage_due_at`, since both would go stale the moment the configured period changes).
- Surfacing the overdue state as a queryable indicator (e.g. an extra field on the existing work-list read) so an agent-facing list can filter or badge it — no UI is built here (out of scope, see below).
- A call into the `FR-WFL-05` scheduled-rule mechanism (`C12`) so an overdue Incident becomes visible to that mechanism for whatever reminder/escalation action is configured; this ticket registers the trigger condition, it does not build the rule engine, the reminder or the escalation action.
- Out of scope: the numeric default period and the default action on expiry (both PRD assumption A11 — not decided by this ticket, not guessed at); the scheduled-rule engine itself and any reminder/escalation delivery (`C12`, `C16`); a dedicated work-list UI surface for the indicator (no `C1` story currently asks for one — see the finding above); re-triggering behavior if a configured workflow lets an Incident return to `New` after leaving it (`DATA-MODEL.md` §8.5 leaves this to the Product Owner, answerable from existing columns whichever way it is decided, and not this ticket's call).

## Acceptance criteria

**Given** the untriaged-period configuration key absent, zero, negative or non-duration **When** the application boots **Then** it fails fast naming the key and does not start.

**Given** an Incident in `New` with no category, older than the configured period **When** the overdue query runs **Then** it is reported overdue for triage.

**Given** an Incident in `New` with no category, within the configured period **When** the overdue query runs **Then** it is not reported overdue.

**Given** an Incident that has left `New` or that already has a category **When** the overdue query runs **Then** it is never reported overdue, regardless of its age.

**Given** the overdue query **When** it executes against a seeded volume **Then** it uses `ix_incident_untriaged` rather than a sequential scan (`EXPLAIN` assertion), consistent with `NFR-PRF-02`'s work-list performance bar.

**Given** an Incident that becomes overdue **When** the `FR-WFL-05` scheduled-rule mechanism evaluates it **Then** it receives the trigger condition this ticket exposes; what that mechanism then does with it is `C12`'s own acceptance, not asserted here.
