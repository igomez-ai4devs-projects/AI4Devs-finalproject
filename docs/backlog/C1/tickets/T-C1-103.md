# [C1] T-C1-103 · Home page at `/` linking to the Incident intake form

## Context

Foundation work with no `C1` story behind it. Source: the Product Owner's explicit decision for the Render prototype (relayed by the architect alongside **ADR-015**, `docs/product/ARCHITECTURE.md` §10): the deployed demo needs **its own page at `/`**, not a redirect, with a title and a "Reportar un problema" link to `/incidents/new` — so a person opening the Render URL lands somewhere legible before ever seeing the intake form. `ADR-015` itself is silent on this page (it is a deploy-topology and persistence decision, §3.3/§6.3/§9/§11.3/§12), which is exactly why it is recorded here rather than mis-cited against that ADR.

**Belongs, eventually, to `C9` (self-service portal) — reassign when that epic is drilled.** `FR-KNW-08` ("§7's Self-Service Portal") is the requirement this page is the first fragment of; `docs/product/PRD.md` §5–§6 places the portal landing surface in `C9`, which has no drilled `user-stories.md`/tickets yet (epic-map, drill order). Ticketed here, in `C1`, at the next free ID, for the same reason `T-C1-10`/`T-C1-101` already live in `C1` despite being "requester portal" content in the strictest sense: `C1` is the only epic with real routed screens today, and the Render demo needs this page to exist *now*, not once `C9` is drilled. **When `C9` is drilled, this ticket's ID is superseded** — the `business-analyst`/`architect-tech-lead` pass for `C9` should re-home this page (or its eventual, fuller replacement) under a proper `US-C9-nn` story, and this file should be marked accordingly at that time. Until then it is deliberately `foundation: true`, `story: —`: no `C1` story asks for a portal landing page, and inventing one to avoid saying so would corrupt the traceability chain this skill exists to protect.

**Composition-root purity, respected.** `apps/web/src/app/app.component.ts`'s own doc comment is explicit: the shell "composes — it never holds business logic, never injects a store or `HttpClient`, and never names an ITSM concept." This page holds no store, no `HttpClient` and no ITSM vocabulary (plain language throughout, per the same `NFR-USE-01` rule `T-C1-10`/`T-C1-101` already follow) — but it does carry real user-facing copy, so per `apps/web/src/app/app.routes.ts`'s own wildcard-route comment ("such a surface is nothing but user-facing copy… its keyed page belongs to a feature slice that owns string sourcing"), it is built as a small routed component inside `libs/incident/feature` — the only frontend feature library that exists today — not inlined into `AppComponent`.

**Routing mechanics.** `apps/web/src/app/app.routes.ts` today resolves `''` to `{ path: '', pathMatch: 'full', children: [] }` — a real, resolvable route with no rendered content, kept exactly so that `apps/web-e2e`'s `harness-smoke.feature` ("the router has settled on the default route") keeps passing. This ticket replaces that empty entry with a **per-component lazy load** (`loadComponent`), the smallest change that keeps the shell's only coupling to a bounded context a lazy import (`ARCHITECTURE.md` §7.1's "BOOT -- lazy loadChildren/loadComponent --> FEAT"), without wrapping one static page in a whole `Route[]` array the way `incidentRoutes` does for a multi-screen surface. `main#main-content`/`router-outlet` still render exactly as `harness-smoke.feature`'s existing scenario asserts — only the routed child changes, from nothing to this page.

**Spanish from day one — this page's own strings are new, not a translation.** The user's decision (relayed with this ticket) is that the whole demo web surface is in Spanish, with every string sourced from `libs/incident/feature/src/lib/incident-messages.ts` (the same file `T-C1-10`/`T-C1-101` already source from), never inline in a template and never through `nestjs-i18n`/Transloco (the same accepted i18n-deferred debt as those two tickets, `CLAUDE.md` §3). This ticket's own strings are authored directly in Spanish; it does **not** translate `T-C1-10`'s or `T-C1-101`'s existing English strings — that is `T-C1-104`, sequenced after this one to avoid two tickets editing the same file's unrelated sections at once.

## Scope

- A new routed component, `HomePageComponent`, in `libs/incident/feature/src/lib/home-page/home-page.component.ts` (+ `.html`, `.scss`), exported from the library's `index.ts` barrel. Standalone, `OnPush`, no injected service, no `HttpClient`, no store.
- `apps/web/src/app/app.routes.ts`: the `''` entry becomes `{ path: '', loadComponent: () => import('@sport-itsm/incident-feature').then((m) => m.HomePageComponent) }`, replacing `{ path: '', pathMatch: 'full', children: [] }`. The wildcard `'**' → redirectTo: ''` entry is unchanged.
- A new `home` section in `INCIDENT_MESSAGES` (`incident-messages.ts`): a page heading, a short introductory line and the link label — all in Spanish, all plain language (no "incidencia"/"ticket"/"SLA" jargon in the heading or intro; the link label may name the action in the same plain terms the intake form itself uses).
- A relative link to the intake form — `<a routerLink="...">`, using Angular's own router link directive (never a plain `<a href="https://…">`), built from `INCIDENT_INTAKE_ROUTE_PATH`/an equivalent exported constant in `incident-routes.ts` rather than a hardcoded `'/incidents/new'` literal repeated a third time.
- A single `<h1>` for the page heading; keyboard-only operability (the link is a normal, focusable anchor — no custom focus handling needed since it is the page's only interactive element); no horizontal scrolling at 360px; hand-built semantic HTML + component-scoped SCSS, no `libs/shared/ui`/`libs/incident/ui` primitive (same deviation `T-C1-10`/`T-C1-101` already carry for this slice).
- Out of scope: any change to `AppComponent`/`app.config.ts`; any search, knowledge-article or catalog content (that is `C9`'s eventual, fuller portal landing — this page is the smallest fragment the demo needs); any i18n infrastructure (Transloco/`nestjs-i18n`); translating `T-C1-10`'s/`T-C1-101`'s existing strings (`T-C1-104`).

## Acceptance criteria

**Given** a browser visiting the deployed (or locally served) web root `/` **When** the page loads **Then** it renders inside the shell's `main#main-content` landmark, presents exactly one `<h1>`, and requires no horizontal scrolling at a 360px viewport.

**Given** the rendered home page **When** its DOM is inspected **Then** it contains exactly one link to the intake form, rendered via `routerLink` (not a plain anchor `href`), whose resolved path is `/incidents/new`.

**Given** a keyboard-only user on the home page **When** they press Tab and then Enter/Space on the focused link **Then** focus visibly lands on the link and activating it navigates to `/incidents/new`, with no pointer interaction required.

**Given** `apps/web-e2e`'s existing `harness-smoke.feature` **When** it is re-run after this ticket **Then** both of its scenarios still pass unchanged — the shell still exposes `app-root main#main-content`, and the router still settles on `/` for a root visit (now rendering `HomePageComponent` instead of an empty routed region).

**Given** every string this page renders **When** its template is grepped for a quoted, user-facing literal **Then** every match is a reference into `INCIDENT_MESSAGES.home`, never an inline literal — and every one of those strings is in Spanish.

**Given** the finding the architect recorded as verification-without-change (no absolute URL anywhere in the frontend surface, since `INCIDENT_API_BASE_URL` and this page's own link both stay relative) **When** `apps/web/src` and `libs/incident/feature/src`/`libs/incident/data-access/src` are grepped for a literal `http://` or `https://` **Then** no match points at the API or at a Render domain — this page's own link is a `routerLink`, never an absolute URL, and no pre-existing file introduced one either.

## Testing methodology (per story / feature)

1. **Understand** — `apps/web/src/app/app.routes.ts`, `apps/web/src/app/app.component.ts`, and `apps/web-e2e/src/features/harness-smoke.feature` (the scenario this change must not break).
2. **Acceptance criteria** — given/when/then above, verifiable against a served `apps/web` and its Cypress harness.
3. **Test data** — none; this page takes no input and calls no API.
4. **Prioritize** — P0: the page renders and the link resolves correctly (this is the whole point of the ticket); P1: keyboard operability and the 360px viewport (already-established WCAG 2.1 AA bar, same as `T-C1-10`); P2: none — the page is small enough that nothing here is "nice to have."
5. **Test type** — E2E (Cypress + Cucumber, `apps/web-e2e`) for the rendered page and the navigation; a component Jest spec for the strings-sourced-from-constants check, which does not need a browser.

> No regression scenario is mandated (this is `foundation: true`, greenfield work, not a gap/defect story), but the **existing** `harness-smoke.feature` scenarios are themselves the regression guard for this exact change — see the acceptance criterion above.
