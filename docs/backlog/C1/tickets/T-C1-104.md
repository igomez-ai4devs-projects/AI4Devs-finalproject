# [C1] T-C1-104 · Translate the intake form and detail screen to Spanish

## Context

Foundation work with no `C1` story behind it. Source: the Product Owner's explicit decision for the Render prototype (relayed alongside `T-C1-103` and **ADR-015**): the whole demo web surface is in Spanish. `T-C1-10` (Requester intake form) and `T-C1-101` (Incident detail component) already source **every** user-facing string from `libs/incident/feature/src/lib/incident-messages.ts` (their own accepted i18n-deferred deviation, `CLAUDE.md` §3) — no template holds an inline literal. That existing discipline is exactly what makes this ticket a **content-only** change: every string this ticket touches already lives in one file, at one export (`INCIDENT_MESSAGES`), so translating it is replacing values, not restructuring components, forms or routing.

**Sequenced after `T-C1-103`, not because it depends on that ticket's code.** Both tickets edit `incident-messages.ts`: `T-C1-103` **adds** a new `home` section (new keys, in Spanish from the start), this ticket **replaces the values** of the pre-existing `intakeForm`/`detail`/`validation`/`ORIGIN_CHANNEL_LABELS`/`PRIORITY_LABELS` exports. Landing them in that order avoids two tickets touching the same file's disjoint sections at once and needing a merge; either order is logically valid.

**What "translate" means here — plain language in the target language, not a literal word-for-word rendering.** `NFR-USE-01` ("plain language, no untranslated ITSM vocabulary") already shaped the English original: no "ticket", "priority", "SLA", "triage" or "incident" reaches a requester-facing string. The Spanish text must hold the same property in Spanish — a plain description of a problem being reported, not a transliterated ITSM glossary. Every dynamic value (`${SHORT_DESCRIPTION_MAX_LENGTH}`, the `Record`-typed maps' keys) stays exactly as coded; only the human-readable string values change.

**Cypress step definitions assert literal English text against the rendered DOM — these must change too, or the suite goes red the moment this ticket lands.** `apps/web-e2e/src/step-definitions/incident-intake.steps.ts` hardcodes four English substrings pulled directly from today's `INCIDENT_MESSAGES`:

| Line(s) | Current assertion | Reads from |
|---|---|---|
| ~189 | `cy.contains('.incident-detail__fields', 'Self-service portal')` | `ORIGIN_CHANNEL_LABELS.portal` |
| ~198 | `.should('contain.text', "couldn't find a report")` | `INCIDENT_MESSAGES.detail.notFoundMessage` |
| ~205 | `.should('contain.text', "isn't in the right format")` | `INCIDENT_MESSAGES.detail.invalidReferenceMessage` |
| ~212 | `.should('contain.text', 'We could not reach the server')` | `COMMON_ERROR_MESSAGES.networkErrorMessage` |

The Gherkin **feature text itself** (`.feature` files, `CLAUDE.md`'s English-language standard for every committed artifact) does **not** change — only the four literal-English fragments embedded inside the step definitions' Cypress assertions, which must now match the Spanish strings this ticket writes. This is exactly the split the `architect-tech-lead` skill draws: the constants file is `frontend-engineer`'s code, the `.steps.ts` assertions are `testing-implementer`'s.

## Scope

- Translate every value (not key) in `INCIDENT_MESSAGES.intakeForm`, `INCIDENT_MESSAGES.detail`, `INCIDENT_MESSAGES.validation`, `COMMON_ERROR_MESSAGES`, `ORIGIN_CHANNEL_LABELS` and `PRIORITY_LABELS` (`libs/incident/feature/src/lib/incident-messages.ts`) to plain, requester-facing Spanish. Keys, object shape, `as const` typing, `${SHORT_DESCRIPTION_MAX_LENGTH}` interpolation and every exported function (`messageForFieldRule`, `isIncidentIntakeField`) are unchanged — this is a values-only edit.
- Update the four literal-English assertions in `apps/web-e2e/src/step-definitions/incident-intake.steps.ts` (table above) to match the new Spanish strings exactly (substring match against the actual translated value, not a full-string match that would break on a future wording tweak).
- Re-read `apps/web-e2e/src/features/incident-intake.feature` and confirm no Gherkin step text itself asserts an English UI string (it does not, today — every step is phrased over behavior, e.g. "the detail page shows a not-found message," never the literal copy) — **no change expected here**, verify rather than edit.
- Out of scope: `T-C1-103`'s own `home` strings (already authored in Spanish); any component logic, template structure, routing or validation *rule* change (only the human-readable text changes); Transloco/`nestjs-i18n` (still deferred); the `incident-intake.steps.ts` fixture's own test-data strings (`persistedReportBody`'s `shortDescription`/`description` — these represent what a requester *typed*, i.e. test data, not UI chrome, and stay as authored).

## Acceptance criteria

**Given** every value in `INCIDENT_MESSAGES` and `ORIGIN_CHANNEL_LABELS`/`PRIORITY_LABELS` **When** the file is read after this ticket **Then** every human-readable string is in Spanish, no ITSM jargon (ticket, prioridad, SLA, triaje, incidencia) appears outside a technical comment, and every dynamic interpolation still resolves correctly.

**Given** the intake form and the detail screen rendered after this ticket **When** they are visually inspected **Then** every label, hint, heading, button and error message is in Spanish, with no English string left anywhere in either component's rendered output.

**Given** `apps/web-e2e/src/step-definitions/incident-intake.steps.ts` **When** it is re-read after this ticket **Then** none of its four `cy.contains(...)`/`.should('contain.text', …)` assertions still names an English substring — each now matches the corresponding Spanish value from `INCIDENT_MESSAGES`.

**Given** `pnpm nx e2e web-e2e` **When** it is run after this ticket **Then** every scenario in `incident-intake.feature` still passes, now against the Spanish-rendered UI.

**Given** `pnpm nx test incident-feature` **When** it is run after this ticket **Then** every existing Jest spec for the intake form and detail components still passes — none of them asserted a literal English string (both components already source every string from the one constants file), so no spec file itself should need editing; if one is found to assert an English literal, that spec is corrected in this same ticket as a discovered gap, not deferred.

## Testing methodology (per story / feature)

Content-only change. No new scenario is added; the existing `AT`-level coverage (`T-C1-10`/`T-C1-101`'s own acceptance criteria, and `incident-intake.feature`'s scenarios) is re-run against the translated strings and must keep passing unchanged in behavior, only in language.

## Testing stack (for realistic recommendations)

**Cypress 15.20 + `@badeball/cypress-cucumber-preprocessor` 28.0**, `apps/web-e2e` · **Jest 29.7** + `jest-preset-angular`, `incident-feature`'s existing component specs.

## Implementation handoff (split by level)

- **Content / unit** (`incident-messages.ts` values, and re-verifying `incident-feature`'s existing `*.spec.ts` files) → `frontend-engineer`.
- **E2E / acceptance** (`apps/web-e2e/src/step-definitions/incident-intake.steps.ts`'s four literal-text assertions) → `testing-implementer` — update the substrings to match this ticket's Spanish text; no Gherkin `.feature` wording changes.
