# [C1] T-C1-21 · Taxonomy persistence, translatable labels, historical integrity and migration

## Context

`US-C1-06` requires that a renamed or deactivated category leaves existing Incidents with **the identifier they were created with**, their historical reporting semantics unchanged (`NFR-DAT-03`), and that a deactivated node stays valid on existing records while no longer being offered for new ones.

That guarantee is a persistence property — a foreign key to a stable identifier rather than a copied label — so it is delivered with the schema that makes it true, not as a separate rule that a later migration could quietly break.

**Confirmed against ADR-014 / `DATA-MODEL.md` §8.5.** This is the ticket that adds `category_id` to `incident_ticket` — nullable on introduction, exactly as §8.5's table states ("`category_id` | Categorization (FR-INC-03) | Target (nullable) | None — `NULL` is true for every existing row"). No backfill: every Incident logged before this migration has no category, and `NULL` already expresses that. This migration also retires `T-C1-06`'s typed mapping-error rejection of a non-`null` `categoryId`, since the slot is now real.

## Scope

- TypeORM entity, mapper and migration for the taxonomy tree in the `incident` schema, keyed by stable identifier with an explicit active flag and ordering column.
- In the **same migration**, add `category_id uuid NULL` (soft ref → the Item-level node) to `incident_ticket`. Incident category reference stored as the **Item-level identifier**, never as a denormalized label.
- Mapper extension: `categoryId` moves from `T-C1-06`'s reject-if-set rule to a real nullable read/write.
- Translatable labels resolved through `nestjs-i18n` keyed by identifier (`NFR-I18N-05`); no user-facing label text in the database as the source of truth for display.
- Repository adapter for the taxonomy, bound in `IncidentModule`; reads reflect changes without a restart.
- Out of scope: the administration use cases (`T-C1-22`); the admin screen (`T-C1-23`).

## Acceptance criteria

**Given** an Incident created under a category **When** that category is later renamed **Then** the Incident still references the same identifier and its historical grouping is unchanged.

**Given** a deactivated node **When** new-Incident category options are read and an existing Incident referencing it is read **Then** the node is absent from the options and still valid on the existing record.

**Given** a taxonomy change **When** it commits **Then** the next read reflects it with no application restart.

**Given** the migration **When** it is run and reverted **Then** it succeeds both ways and leaves no residual object.
