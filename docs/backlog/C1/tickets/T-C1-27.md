# [C1] T-C1-27 · Matrix persistence, configuration versioning, migration and fail-fast boot validation

## Context

`US-C1-09` requires a matrix change to apply to subsequent derivations while **Incidents already in flight keep the configuration version they were created under** (`NFR-CFG-02`), and requires the application to **fail fast** at boot when the matrix is missing or incomplete rather than silently falling back to a default.

Versioning and boot validation ship with the schema because a version column added later cannot retroactively pin the records created before it.

**Corrected by ADR-014 (`DATA-MODEL.md` §8.5, decision M15).** `priority_matrix_id` is not pinned at Incident creation — an Incident is logged with no Priority and therefore governed by no matrix yet (§8.5: "an unassessed Incident has no Priority and is governed by no matrix yet"). It is pinned at the Incident's **first derivation** (`T-C1-30`) and never changed afterwards. This ticket's own `incident_priority_matrix` table, its version column and its seed/boot-validation behavior are unaffected; only the wording of what happens on the `incident_ticket` side changes, and that side's actual column (`priority_matrix_id`, nullable, added by `T-C1-30`) is out of this ticket's scope — see `T-C1-30`.

## Scope

- TypeORM entity, mapper and migration for the matrix, with an explicit configuration version.
- Incident records store the matrix version applied at the Incident's **first derivation**, not at creation; later derivations for an in-flight Incident resolve that same pinned version.
- Seed migration providing a documented default matrix so a fresh environment boots.
- Boot-time validation in `apps/api` asserting a complete matrix exists; on failure the application logs the reason and does not start.
- Out of scope: the aggregate invariant (`T-C1-26`); the screen (`T-C1-28`); the `incident_ticket.priority_matrix_id` column and its `NULL`-until-derived nullability, added by `T-C1-30` in the same migration as the other assessment columns (ADR-014).

## Acceptance criteria

**Given** an Incident first derived under matrix version *n* **When** the matrix is changed to version *n+1* and that Incident is re-derived **Then** it still resolves version *n*, and a newly created Incident, once first derived, resolves *n+1*.

**Given** an incomplete or absent matrix **When** the application boots **Then** it fails fast with a message naming the missing combination or the missing configuration, and does not start.

**Given** a fresh database **When** migrations run **Then** the documented default matrix is present and the application boots.

**Given** the migration **When** it is run and reverted **Then** it succeeds both ways and leaves no residual object.
