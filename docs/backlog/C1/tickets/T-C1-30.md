# [C1] T-C1-30 · Server-side derivation, the not-yet-derived state and `PriorityChanged`

## Context

`US-C1-08` requires the server to derive and persist Priority whenever Impact or Urgency is set or changed; requires an Incident whose assessment is incomplete to report Priority as **explicitly "not yet derived"** rather than defaulting to a middle value that could be mistaken for a real assessment; and requires every Priority change, from any cause, to publish an event carrying the previous and new Priority **and the reason for the derivation**.

That event is what `C7` consumes to re-evaluate SLA targets (`FR-SLA-04`) and what `C18` records. This epic publishes it; neither consumer is written here.

**Already built in `libs/incident/domain` by `T-C1-05` — do not re-derive.** `Incident.log()` already creates every Incident with `impact`, `urgency` and `priority` all `null`, and `incident.aggregate.spec.ts` (AC3) already asserts this reads as explicitly not-yet-derived, never a disguised default — exactly the guarantee `FR-INC-04`'s revised text requires. This ticket does not rebuild that guarantee at creation; it only has to **preserve** it through partial re-assessment (Impact set without Urgency, or vice versa) and **surface** the not-yet-derived state as an explicit value in the contract, which is new work `T-C1-05` does not cover.

**This ticket carries the assessment-columns migration (ADR-014 / `DATA-MODEL.md` §8.5, decision M14/M15) — chosen over `T-C1-27`.** `base_impact`, `assessed_impact`, `urgency`, `priority`, `priority_overridden`, `priority_override_justification` and `priority_matrix_id` are introduced by "the first behavior that writes them" (ADR-014 rule 3), and that behavior is `AssessIncidentUseCase` persisting a derivation — not the matrix's own configuration table, which `T-C1-27` already owns and which no Incident row ever writes to directly. Bundling the migration with the use case that is its only writer also lets the mapper and the migration land in the same commit, which is what makes the four coherence checks (`ck_incident_impact_pair`, `ck_incident_priority_derivation`, `ck_incident_priority_provenance`, the tightened `ck_incident_priority_override`) verifiable against real persistence rather than asserted on paper. **Sizing note (skill exception, recorded per its own rule):** this pushes the ticket to 3.5h, over the 3h cap. Splitting the migration into its own ticket would leave either a schema with columns nothing writes to yet, or a use case that authorizes and derives but cannot persist its own output — the exact "artificial dependency" the cap's exception clause exists for, since both halves share the one migration and the one mapper extension.

## Scope

- Assessment mutators on the `Incident` aggregate that re-derive Priority through `PriorityCalculator` on every Impact or Urgency change.
- An explicit not-yet-derived Priority state, distinct from every real Priority level, surfaced in the contract rather than as a null the client must interpret.
- `PriorityChanged` domain event carrying previous Priority, new Priority, the derivation reason and the matrix version applied.
- `AssessIncidentUseCase` in `libs/incident/application` authorizing the prioritization permission and publishing post-commit.
- **Migration** adding `base_impact`, `assessed_impact`, `urgency`, `priority` (all nullable — `NULL` is the persisted "not yet derived" state, never a default level), `priority_overridden` (`NOT NULL DEFAULT false`), `priority_override_justification` (nullable) and `priority_matrix_id` (nullable FK → `incident.incident_priority_matrix`, only valid once `T-C1-27` exists) to `incident_ticket`, plus `ck_incident_impact_pair`, `ck_incident_priority_derivation`, `ck_incident_priority_provenance` and `ck_incident_priority_override`. **No backfill** — "not yet assessed" is already true of every existing row (§8.5).
- Mapper extension: these seven slots move from the T-C1-06 read-null/reject-if-set rule to real read/write; T-C1-06's typed mapping error for them is retired here, and its equivalent check for the columns still absent (`categoryId`, `competitionAffectsInProgress`, `affectedSubject`, `assignment`) is unaffected.
- Out of scope: the override (`T-C1-32` → `T-C1-34`); the flag-driven derivation (block E); the SLA re-evaluation itself (`C7`, reached through `T-C1-58`); the `incident_priority_matrix` table itself (`T-C1-27`).

## Acceptance criteria

**Given** an Incident with Impact and Urgency assessed **When** either is changed **Then** Priority is re-derived server-side, persisted, and exactly one `PriorityChanged` event is published after commit carrying previous, new, reason and matrix version.

**Given** an Incident whose Impact or Urgency is not yet assessed **When** it is read **Then** Priority is the explicit not-yet-derived value, and no middle-level Priority is returned.

**Given** a client that posts a Priority **When** the assessment use case executes **Then** the posted value is ignored and the derived value is persisted.

**Given** an actor without the prioritization permission **When** they attempt to assess **Then** it is denied with `403` and nothing changes.

**Given** the migration **When** it is run and reverted **Then** it succeeds both ways, leaves no residual object, and requires no backfill because every pre-existing row is already unassessed.
