# [C1] T-C1-43 · `SetCompetitionInProgressFlagUseCase` — the only write path, agent-authorized

## Context

`US-C1-12` requires the flag write to be **reachable only from the agent-invoked use case with an actor holding the agent permission**, and an agent without that permission to be denied with `403` with nothing changed. `ARCHITECTURE.md` §8 shows the flag on its own endpoint with its own use case and its own authorization check, precisely so no other operation can carry it as a side effect.

This is the singleness half of “agent-only and never automatic”. `T-C1-45` proves the never-automatic half; `T-C1-44` closes the inbound field paths.

**Gap found and closed this pass: nothing in block E owned the `competition_affects` migration.** `DATA-MODEL.md` §8.5 introduces `competition_affects` + `competition_justification` + `competition_flag_set_by` + `competition_flag_set_at` + `ck_incident_competition_flag` with "the competition flag (FR-INC-05)" — and this use case is the **only write path** for that flag (the ticket's own title), so, per ADR-014 rule 3 ("a column arrives with the first behavior that writes it"), it is the migration this ticket carries. No other block-E ticket persists to `incident_ticket`: `T-C1-37` migrates the separate `incident_impact_uplift` configuration table, not this one. **Sizing note (skill exception, recorded per its own rule):** this pushes the ticket to 3.5h. Splitting the migration out would leave the one use case that writes these columns unable to persist its own output — the same shared-migration argument `T-C1-30` and `T-C1-50` already record for their own columns.

## Scope

- `SetCompetitionInProgressFlagUseCase` in `libs/incident/application`, authorizing the flag permission through the resolved `Actor`, applying `T-C1-40` and publishing the causal event of `T-C1-42` post-commit.
- Its own HTTP route in `apps/api` and its own contract DTO, separate from every Incident update route.
- Removal of the flag from every other command shape in the application layer, so no other use case can accept it.
- **Migration** adding `competition_affects boolean NOT NULL DEFAULT false`, `competition_justification varchar(500) NULL`, `competition_flag_set_by uuid NULL` (soft ref → `iam.iam_user`) and `competition_flag_set_at timestamptz NULL` to `incident_ticket`, plus `ck_incident_competition_flag`. No backfill: the `false` default is already true of every existing row (§8.5).
- Mapper extension retiring `T-C1-06`'s reject-if-set rule for `competitionAffectsInProgress`.
- Out of scope: the field rejection at the DTO boundary on other routes (`T-C1-44`); the no-automated-path proof (`T-C1-45`); the clearing path (`T-C1-46`); the UI (`T-C1-48`); the separate `incident_impact_uplift` table and its own migration (`T-C1-37`).

## Acceptance criteria

**Given** an agent holding the flag permission and a justification **When** the use case executes **Then** the flag is set, the uplift and re-derivation apply, and the causal event is published after commit.

**Given** an actor without the flag permission **When** they invoke the use case directly and separately through its HTTP route **Then** both are denied with `403`, nothing is persisted and no event is published.

**Given** every other use case in `libs/incident/application` **When** their command shapes are enumerated **Then** none accepts the competition-in-progress flag as an input.

**Given** the route table **When** it is enumerated **Then** exactly one route writes the flag, and it is the one this ticket adds.

**Given** the migration **When** it is run and reverted **Then** it succeeds both ways, leaves no residual object, and requires no backfill because `false` is already true of every pre-existing row.
