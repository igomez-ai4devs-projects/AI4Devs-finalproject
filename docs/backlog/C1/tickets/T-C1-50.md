# [C1] T-C1-50 · Transition-rule configuration: persistence, migration and hot reload

## Context

`US-C1-15` requires the configured transitions to be **changed by an administrator, take effect without a restart, and be audited**. This is the “configuration as data” rule of `ARCHITECTURE.md` §9 applied to the lifecycle.

The `StateModel` primitive comes from `C10`; the per-context configuration mechanism is `C12`. This ticket delivers the `incident` context storage and reload path, not a general configuration framework.

**This is the ADR-014 / `DATA-MODEL.md` §8.5 lifecycle migration.** This ticket is the one that creates `incident_workflow` and `incident_workflow_state` and seeds the default version (§8.5's own words for the introduction point), so it is also the migration that adds `incident_ticket.workflow_id`, `.state_id` and `.state_category` — the only column group in the whole ADR-014 table that is `NOT NULL` **and** arrives after rows already exist, which is exactly the case §8.5 requires a lossless backfill for. **Sizing note (skill exception, recorded per its own rule):** bundling the transition-rule tables, the lifecycle columns, their backfill and their `SET NOT NULL` in one migration pushes this ticket to 3.5h. Splitting the backfill into a separate ticket would require it to re-derive the same "every existing row is provably still in `New`" argument this ticket already has to make to seed `incident_workflow`/`incident_workflow_state` in the first place — an artificial split of one migration's data-writing statements.

**Second pass — `state_category_enum` gains `new` (M17), and the triage-gate check is renamed and widened (FR-INC-19, PRD §14.10).** The enum this migration creates is no longer the five-value `open, pending, resolved, closed, cancelled` set: it gains a sixth value, **`new`**, the category of the initial state and of no other, so that "this Incident is still in `New`" is row-local and non-configurable — required both for `ck_incident_triaged_beyond_new` to read it in a `CHECK` and for `FR-INC-20`'s untriaged-period sweep to filter on it without joining the configurable workflow-state table. This migration also adds `ck_incident_workflow_state_new_is_initial` on `incident_workflow_state`: `(category = 'new') = is_initial` — no configuration can classify a non-initial state as `new`, or the initial state as anything else. The backfill target changes accordingly: every pre-existing row backfills to the seeded initial state, category **`new`** (not `open` — `open` is now every *other* active state). The check this migration used to add as `ck_incident_categorized_beyond_new` is superseded by **`ck_incident_triaged_beyond_new`**, per `DATA-MODEL.md` §8.1: `state_category IN ('new','cancelled') OR (category_id IS NOT NULL AND assessed_impact IS NOT NULL AND urgency IS NOT NULL AND priority IS NOT NULL AND service_id IS NOT NULL)` — it now also requires the Impact/Urgency assessment (hence Priority) and the affected Service, per `FR-INC-19`, not the category alone. It is still added here because this is the **last** of the three migrations whose columns it reads (categorization, `T-C1-21`; priority derivation, `T-C1-30`; the lifecycle, this ticket) — confirmed against the current block order (C, D, F). `cancelled` is deliberately left out of the constrained set, pending PRD §14.10 open point 2 (whether cancellation is exempt from the gate) — this migration does not decide that question, it only leaves both future outcomes representable. Added **validated**, never `NOT VALID`: every row has just been backfilled to `new` when this check is added, so it holds by construction.

## Scope

- TypeORM entity, mapper and migration for `incident_workflow`, `incident_workflow_state` and the Incident transition rules, plus a seed migration providing the `FR-INC-06` default transition set and version so a fresh environment boots.
- `incident.state_category_enum` created with **exactly** `new`, `open`, `pending`, `resolved`, `closed`, `cancelled` — `new` identifies the initial, untriaged state and no other (M17).
- `ck_incident_workflow_state_new_is_initial` on `incident_workflow_state`: `(category = 'new') = is_initial`.
- **In the same migration:** add `workflow_id`, `state_id` (both nullable at first) and `state_category` to `incident_ticket`; backfill every existing row to the seeded version's `is_initial` state (`New`, category **`new`**) and insert one `incident_state_transition` creation row per existing ticket (`from_state_id NULL`, `to_state_id` = the seeded initial state, `occurred_at = created_at`, `actor_type = 'user'`, `actor_user_id = created_by`); then `SET NOT NULL` on `workflow_id` and `state_id` (`state_category` was never nullable). This backfill is exact, not approximate: before this migration no transition exists, so every prior row is provably still in `New`, logged by `created_by` at `created_at` (ADR-014, §8.5).
- `ck_incident_resolution` and **`ck_incident_triaged_beyond_new`** (`state_category IN ('new','cancelled') OR (category_id IS NOT NULL AND assessed_impact IS NOT NULL AND urgency IS NOT NULL AND priority IS NOT NULL AND service_id IS NOT NULL)` — `FR-INC-03` + `FR-INC-19`), both of which reference `state_category` and so cannot exist before this migration. Added validated, never `NOT VALID`.
- `ix_incident_untriaged` — `(created_at)` partial `WHERE state_category = 'new'` — and `ix_incident_worklist` — `(priority, created_at)` partial `WHERE state_category IN ('new','open','pending')` — both buildable for the first time here, since `state_category` is this migration's own column and `priority` already exists (`T-C1-30`). **Gap found and closed this pass:** no earlier `C1` ticket created either index, though `DATA-MODEL.md` §16 has always specified them. `ix_incident_group_queue` and `ix_incident_mine` are **not** added here — they also filter on `assigned_group_id`/`assigned_user_id`, which do not exist until `T-C1-73` — and are flagged as a finding for that ticket rather than invented here.
- Repository adapter feeding the `StateModel` instance, with reads reflecting a change on the next transition and no restart required.
- `TransitionRulesChanged` domain event published on change for the audit trail (`FR-AUD-05`).
- Configuration version pinned on in-flight Incidents per `NFR-CFG-02`, consistent with `T-C1-27` and `T-C1-37`: `workflow_id` is pinned at creation (every Incident has a lifecycle state from birth), unlike `priority_matrix_id` which pins at first derivation (`T-C1-30`).
- Mapper extension retiring T-C1-06's typed mapping error for the lifecycle slots.
- Out of scope: the state model itself (`T-C1-49`); the administration screen, which belongs to the Admin Console surface and is not required by any `C1` story; the untriaged-period sweep and the "overdue for triage" indicator that reads `ix_incident_untriaged` (`FR-INC-20`, new ticket `T-C1-102`); `ix_incident_group_queue`/`ix_incident_mine` (flagged for `T-C1-73`, see above).

## Acceptance criteria

**Given** a transition rule change **When** it commits **Then** the next transition attempt honours it with no application restart.

**Given** a fresh database **When** migrations run **Then** the default transition set of `FR-INC-06` is present and the application boots.

**Given** a transition rule change **When** it commits **Then** exactly one `TransitionRulesChanged` event is published after commit with the actor and the previous and new rule set.

**Given** an Incident row that existed before this migration **When** the migration runs **Then** it ends in the seeded version's initial state with `state_category = 'new'` and exactly one creation transition row (`from_state_id NULL`, `occurred_at` equal to its own `created_at`, `actor_user_id` equal to its own `created_by`), and `workflow_id`/`state_id` are `NOT NULL` on every row once the migration completes.

**Given** the seeded lifecycle configuration **When** `incident_workflow_state` is inspected **Then** exactly the initial state carries category `new`, enforced by `ck_incident_workflow_state_new_is_initial`; no other state can be classified `new` and the initial state cannot be classified anything else.

**Given** an Incident outside `New` and `Cancelled` **When** it is missing its category, its Impact/Urgency assessment or its affected Service **Then** `ck_incident_triaged_beyond_new` rejects the row; an Incident with all four present, or one still in `New` or `Cancelled`, is accepted.

**Given** the migration **When** it is run and reverted **Then** it succeeds both ways (the revert drops the backfilled transition rows, the new indexes and the new columns without touching any other data) and leaves no residual object; run-revert-run produces an identical outcome.
