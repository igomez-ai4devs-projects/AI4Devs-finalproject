# [C1] T-C1-72 · `ResolverAssignment` and the append-only assignment history

## Context

`US-C1-24` requires that on reassignment the current assignee changes and **a new assignment record is appended; previous assignments are never overwritten or deleted** — and that the history shows every assignment in order with the group or agent, the actor who made the change and the timestamp, so the full path is reconstructable.

That history is also the input to First Contact Resolution (`US-C1-32`, `T-C1-79`): an Incident reassigned at least once does not qualify. Building the history as append-only from the start is what makes FCR derivable rather than guessed.

**Resolver Groups are owned by `C14`** and live in the `identity-access` context. They are **referenced here, never defined** — no `C14` ticket is written in this epic.

**Verified this pass against `DATA-MODEL.md` §8.1/§8.5 — the persisted `incident_ticket.assigned_group_id`/`assigned_user_id`/`assigned_at` columns are `T-C1-73`'s, not this ticket's.** The dictionary lists those three columns directly on `incident_ticket` (soft refs into `iam`, feeding `ck_incident_assessed_before_assignment` and the `ix_incident_group_queue`/`ix_incident_mine` work-list indexes), introduced "with Assignment" — and, per ADR-014 rule 3 ("a column arrives with the first behavior that writes it"), the same reasoning that put the assessment-columns migration on `T-C1-30` rather than a sibling domain ticket, and the competition-flag migration on `T-C1-43` rather than a sibling one, puts this migration on `T-C1-73`'s `ReassignIncidentUseCase` — the one use case that ever writes an assignment. This ticket stays scoped to the **aggregate's own, in-memory** current-assignee derivation and the **append-only history table** (`incident_assignment_history`), which has no writer of its own outside the same use case either, but exists independently of whether `incident_ticket` also carries a denormalized pointer.

## Scope

- `ResolverAssignment` value object in `libs/incident/domain` holding the target — Resolver Group reference or individual agent reference — the acting actor and the `ClockPort` timestamp.
- Append-only assignment history on the aggregate: no mutator that replaces or removes a past entry exists.
- TypeORM entity, mapper and migration for **`incident_assignment_history` only** — the append-only table — with the aggregate's own current-assignee accessor derived in memory from the latest entry.
- Out of scope: the reassignment use case and its event (`T-C1-73`); the persisted `incident_ticket.assigned_group_id`/`assigned_user_id`/`assigned_at` columns and `ck_incident_assessed_before_assignment`, both `T-C1-73`'s migration (see the note above); Resolver Group definition, membership and routing rules (`C14`); escalation (`T-C1-75` onward).

## Acceptance criteria

**Given** an Incident reassigned three times **When** the history is read **Then** it contains four entries in order — the original plus three — each with target, actor and timestamp, and none overwritten.

**Given** the aggregate **When** its API is inspected **Then** no operation removes or edits a past assignment; append-only holds by absence of capability.

**Given** the aggregate's current assignee **When** it is read in memory **Then** it is derived from the latest history entry, so the two can never disagree — the persisted, indexable copy of this same fact is `T-C1-73`'s.

**Given** the migration **When** it is run and reverted **Then** it succeeds both ways and leaves no residual object.
