# [C1] T-C1-73 · `ReassignIncidentUseCase`, the `IncidentAssigned` event and the assignment migration

## Context

`US-C1-24` requires a reassignment to publish an assignment event that **`C16` consumes to notify and `C18` records**, with Resolver Groups **owned by `C14` and referenced, not defined, here**.

The dependency direction matters: this epic publishes the event and stops. No notification template and no audit entry is written in `C1`.

**Resolved this second pass — the assignment guard is `FR-INC-19` (PRD §14.10), not an unnumbered Product Owner decision.** `FR-INC-19` states it directly: "the system MUST also prevent an Incident from being **assigned** to a Resolver Group or to an individual agent — whether by manual assignment, self-assignment (FR-QUE-03), reassignment (FR-INC-12) or an assignment rule (FR-WFL-02/03) — until Impact and Urgency have been assessed." This is the assignment half of the same requirement `T-C1-49` enforces on exit from `New`; the two are separate gates on separate operations (a lifecycle transition vs. setting an assignee) and this ticket owns its own half rather than delegating to `T-C1-49`'s `transitionTo()`, which this use case does not necessarily call.

**Story attribution (F32, this pass).** `docs/backlog/C1/user-stories.md` now gives `FR-INC-19` its own story, `US-C1-33`, rather than folding it into `US-C1-24`. This ticket's `story:` front matter **stays `US-C1-24`**: it is chiefly about assignment mechanics — `ReassignIncidentUseCase`, the `IncidentAssigned` event, the append-only history, the target-reference validation — and that is the bulk of its scope and of `US-C1-24`'s own acceptance criteria. The one guard this ticket adds against an unassessed Incident (`FR-INC-19`) is `US-C1-33`'s own acceptance criterion on the assignment path — the second AC below traces to `US-C1-33`, cross-referenced here rather than reparented, since the ticket's real identity remains reassignment.

**Gap found and closed this pass — this ticket carries the `assigned_*` migration, moved here from `T-C1-72`.** `DATA-MODEL.md` §8.1/§8.5 lists `incident_ticket.assigned_group_id`, `.assigned_user_id` and `.assigned_at` (soft refs into `iam`) plus `ck_incident_assessed_before_assignment` as columns of `incident_ticket` itself — not of the append-only `incident_assignment_history` table `T-C1-72` migrates — introduced "with Assignment". Per ADR-014 rule 3 ("a column arrives with the first behavior that writes it"), the same reasoning already applied to `T-C1-30` (assessment columns, not `T-C1-27`'s matrix ticket) and `T-C1-43` (competition-flag columns, not a sibling block-E domain ticket), this use case is that first — and only — writer, so the migration belongs here. `T-C1-72`'s own value object and history table are unaffected; this ticket keeps the two in agreement by writing both inside the same transaction. **Sizing note (skill exception, recorded per its own rule):** this pushes the ticket to 3.5h. Splitting the migration out would leave the one use case that writes `assigned_group_id`/`assigned_user_id` unable to persist its own output — the same shared-migration argument `T-C1-30`, `T-C1-43`, `T-C1-49` and `T-C1-50` already record for their own columns. **Sequencing:** `ck_incident_assessed_before_assignment` reads `assessed_impact`/`urgency`, so this migration runs after `T-C1-30`.

## Scope

- `ReassignIncidentUseCase` in `libs/incident/application`, authorizing the assignment permission and appending to the history of `T-C1-72`.
- Validation that the target Resolver Group or agent reference exists, through a port resolved against `C14` at the composition root — never by importing `identity-access` from `incident`.
- **New:** a guard refusing assignment with a typed domain error naming the missing assessment when Impact or Urgency is not yet set (`FR-INC-19`), checked before the target-reference validation so the two refusal reasons are never conflated.
- `IncidentAssigned` domain event carrying previous target, new target, actor and timestamp, published post-commit.
- **Migration** adding `assigned_group_id uuid NULL` (soft ref → the Resolver Group concept `C14` owns), `assigned_user_id uuid NULL` (soft ref → `iam.iam_user`) and `assigned_at timestamptz NULL` to `incident_ticket`, plus `ck_incident_assessed_before_assignment` (`(assigned_group_id IS NULL AND assigned_user_id IS NULL) OR (assessed_impact IS NOT NULL AND urgency IS NOT NULL)`). No backfill: no row is assigned before these columns exist, so the check holds by construction.
- The use case writes the denormalized `assigned_group_id`/`assigned_user_id`/`assigned_at` on `incident_ticket` and appends to `incident_assignment_history` (`T-C1-72`) in the **same transaction**, so the two can never disagree — this is what lets `T-C1-72`'s own aggregate-level accessor and this ticket's persisted, indexable columns agree without a join.
- Contract DTOs and the HTTP route.
- Out of scope: Resolver Group definition and routing (`C14`); notification (`C16`); audit persistence (`C18`); escalation kinds (`T-C1-75`, `T-C1-77`); the exit-from-`New` gates on the same Impact/Urgency inputs, which are `T-C1-49`'s; the `ix_incident_group_queue`/`ix_incident_mine` work-list indexes over these new columns, flagged in `T-C1-50` as a finding rather than built speculatively here.

## Acceptance criteria

**Given** an assigned Incident **When** an agent reassigns it to another Resolver Group or individual **Then** the current assignee changes on `incident_ticket`, a history entry is appended to `incident_assignment_history`, and exactly one `IncidentAssigned` event is published after commit.

**Given** an Incident whose Impact or Urgency is not yet assessed **When** assignment is attempted **Then** it is refused with a typed domain error naming the missing assessment (`FR-INC-19`), and nothing is appended to the history or written to `incident_ticket`.

**Given** a target reference that does not resolve **When** reassignment is attempted **Then** it is refused with a typed error and nothing is appended.

**Given** an actor without the assignment permission **When** they attempt it **Then** it is denied with `403` and nothing changes.

**Given** the dependency graph **When** it is inspected **Then** no `scope:incident` project depends on `scope:identity-access`; the reference resolves through a port bound in `apps/api`.

**Given** the migration **When** it is run and reverted **Then** it succeeds both ways, leaves no residual object, and requires no backfill because no row is assigned before it runs.
