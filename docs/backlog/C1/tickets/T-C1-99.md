# [C1] T-C1-99 · `GetIncidentByReference` use case and the repository's read method

## Context

The Product Owner's re-cut of delivery slice 1 ("register an Incident and see it, as simply as possible") settled the "see it" half as **detail by reference** — `GET /incidents/{reference}` — rather than echoing the `POST` response, because an echo shows what was typed, not what was persisted. This ticket is the read side: nothing here writes.

Sequenced after `T-C1-05` (the aggregate) and `T-C1-06` (the repository adapter and migration), both of which it extends rather than duplicates.

## Scope

- **Deviates from this ticket's own wording below, decided and ratified — see the closing note.** `findByReference(reference)` is **not** added to `IncidentRepositoryPort`. It is declared on a new, narrower port, `IncidentReadRepositoryPort` (`libs/incident/domain/src/lib/incident-read-repository.port.ts`), with its own injection token `INCIDENT_READ_REPOSITORY`, kept **independent** of `IncidentRepositoryPort` (no `extends` in either direction). `TypeOrmIncidentRepository` (`T-C1-06`) implements **both** interfaces explicitly — one adapter, two ports. `T-C1-100` binds that single instance to both tokens.
- `GetIncidentByReferenceUseCase` in `libs/incident/application`: depends on `IncidentReadRepositoryPort` **only** — the type-level guarantee AC3 requires, not just a behavioral one. Takes an already-constructed `TicketReference` (never a raw `string`; parsing/format validation of the path parameter is `T-C1-100`'s concern, at the HTTP boundary, not this use case's). Returns `GetIncidentByReferenceResult = Result<IncidentSnapshot, IncidentNotFoundOutcome>` (`@sport-itsm/shared-util`'s existing `Result`) — a **snapshot**, produced by the aggregate's own `toSnapshot()`, never the `Incident` aggregate itself, so nothing downstream can call a mutating aggregate method on what this use case hands back. `IncidentNotFoundOutcome` is a plain typed record (`{ reason: 'INCIDENT_NOT_FOUND', reference }`), not a thrown exception.
- `execute(reference: TicketReference)` takes no actor/context parameter yet, matching the "no authorization narrowing" decision below — **not a permanent signature**: the moment `US-C1-06`'s predicates exist, this becomes `execute(reference, context)`, a small additive change at this one call site (approved by the user).
- No authorization narrowing in this ticket — this slice has no scoped visibility yet (`FR-IAM-03` predicates land with `C10`/`C1` blocks not in this slice); the use case is deliberately open to any resolved actor. **Not a permanent decision** — the moment `US-C1-06`'s predicates exist, this use case gates on them, and that is a scope gap to report at that time, not something this ticket pre-empts by guessing.
- Jest unit tests: found, not-found, and that no write path is reachable from this use case — proved at the type level (the port's own shape), not only by a double's recorded behavior.
- Out of scope: the HTTP adapter and its response contract (`T-C1-100`); the detail component (`T-C1-101`); any visibility predicate; wiring either injection token into `IncidentModule` (`T-C1-100`'s job, not this one's).

## Acceptance criteria

**Given** a persisted Incident and its exact reference **When** the use case executes **Then** it returns the Incident's full current state.

**Given** a reference that matches no Incident **When** the use case executes **Then** it returns a typed not-found outcome, never a generic error and never a thrown exception the caller must guess at.

**Given** the use case **When** it is unit-tested **Then** it runs against a stubbed repository with no HTTP and no database, and no method on the port it calls can mutate a row.

**Given** the application library **When** it is inspected **Then** this use case imports no framework, no ORM and no HTTP.

## Closing note — port relationship decided: independent, not `extends` (ISP)

This ticket's own Scope, as first written, asked for `findByReference()` to be "added to `IncidentRepositoryPort`" — but that port also declares `save()`, `nextIdentity()` and `nextReference()`. Following that wording literally would have made AC3 ("no method on the port it calls can mutate a row") false by construction: the type `GetIncidentByReferenceUseCase` depends on would carry a write method whether or not it is ever called. The build instead declared a second, narrower port — `IncidentReadRepositoryPort` — so the use case's dependency is read-only *at the type level*, per Interface Segregation (`sport-itsm-engineering-principles`) and the domain-owned-ports rule (`sport-itsm-architecture` §2–§3: ports are declared in the domain, dependencies point inward only). This is reported as a deviation from the Scope's literal wording, not a silent substitution.

**Decided and ratified here: the two ports stay independent.** `IncidentRepositoryPort` does **not** gain `findByReference()`, and `IncidentReadRepositoryPort` does **not** gain `save()`/`findById()`/`nextIdentity()`/`nextReference()`, and neither `extends` the other. Two reasons, both sufficient on their own:

1. **Blast radius on existing implementers.** `IncidentRepositoryPort` already has real implementers this ticket has no license to touch — the composition-root test doubles `apps/api/src/app/incident/log-incident.dispatcher.spec.ts` and `log-incident.fixed-actor.spec.ts`. Widening that port by extension (in either direction) would force both doubles to also implement `findByReference()`, which is out of this ticket's boundaries regardless of its technical merit.
2. **No future consumer needs the merge.** A write use case that mutates an existing Incident (triage, assign) already has `IncidentRepositoryPort.findById(id)` to load the aggregate before `save()`. Reference-to-identity resolution is a read concern, satisfied by `IncidentReadRepositoryPort` at whichever layer first holds only a reference (the controller, or a thin resolution step ahead of the write use case) — nothing about a write use case's job requires the write port itself to carry a reference-based lookup. Keeping the ports independent costs one duplicated method signature between two files and buys zero blast radius on `IncidentRepositoryPort`'s current implementers.

No follow-up ticket is needed for this decision — it is closed by this note. `T-C1-100`'s Scope now states explicitly that it binds the single `TypeOrmIncidentRepository` instance to both `INCIDENT_REPOSITORY` and `INCIDENT_READ_REPOSITORY`.
