# [C10] T-C10-24 · `Session` aggregate, port, entity and migration — RETIRED

## Why this ticket is retired, not implemented

This ticket built a server-side `Session` aggregate, `SessionRepositoryPort`, a TypeORM `SessionEntity` and a migration creating a session table — a stored, per-request-checked record of live sessions.

The Product Owner has since resolved the assurance-level question this design assumed an answer to. `docs/product/PRD.md` §14.8 ("Recorded decision — session security posture") normatively adopts **device-bounded termination** and states: *"no artifact derived from this PRD may require access to be validated against a central session record on each request, and none may require a stored, per-request-updated record of live sessions."* This ticket's entire deliverable is exactly that record. It is not a partial fit needing adjustment — its reason for existing is gone.

`FR-IAM-06` (inactivity + maximum lifetime) and `FR-IAM-08` (sign-out) are now satisfied without any server-held session state: inactivity and sign-out are properties of the device (client-side token discard and an idle timer), and the maximum session lifetime is the JWT's own `exp` claim, fixed at issuance (`T-C10-26`) from validated configuration (`T-C10-56`) — never extended, never checked against a stored record.

## What replaced this ticket's downstream consumers

- `T-C10-25` (`AuthenticateUser`) no longer creates a session or depends on `SessionRepositoryPort`; it issues a token directly.
- `T-C10-26` (`TokenIssuerPort`) no longer carries a session identifier claim; the token's `exp` **is** the maximum-lifetime bound.
- `T-C10-28` (global guard) no longer validates a session record — signature and expiry are the whole check.
- `T-C10-32` and `T-C10-33` (the sign-out use case and its HTTP adapter) are **also retired** — see their own files — because there is no session record left for either to terminate.
- `T-C10-57` (sliding inactivity expiry) is **regenerated**, not retired, with a much narrower scope: sourcing the JWT's fixed lifetime from configuration and proving no sliding occurs.
- `T-C10-59`/`T-C10-60` (step-up re-authentication) are regenerated to verify a presented credential synchronously per privileged request, storing nothing.

## Numbering

`T-C10-24` is retired and **is not reused.** Ticket IDs in this backlog are stable and appended at the next free ID (the same rule already applied to `T-C10-68`–`T-C10-71`); a retired ID is no exception — reusing it would let a future, unrelated ticket answer to a number this file already answered to, for a different design, breaking traceability for anyone who cited `T-C10-24` before this revision.
