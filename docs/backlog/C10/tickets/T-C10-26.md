# [C10] T-C10-26 · `TokenIssuerPort` and the `@nestjs/jwt` adapter

## Context

`US-C10-01` requires a signed JWT access token whose claims carry the user identifier, the display name, the assigned role identifiers and an expiry. JWT is a framework concern, so the application layer depends on a port and the signing lives in an infrastructure adapter, consistent with `T-C10-20`.

**Defect fixed here, and one piece of `T-C10-57`'s retired scope absorbed.** As first written, this ticket issued a token "for a resolved identity and a session" and carried a `session id` claim — `T-C10-24`'s aggregate, now retired (`PRD` §14.8 forbids the stored session it represented). `US-C10-01`'s own claim list never asked for a session identifier, so it is dropped, not replaced. Separately, `T-C10-57` ("sliding inactivity expiry") depended on the same retired aggregate for a different reason — a server-tracked idle window — and is regenerated with a much smaller scope of its own; the one piece of it that belongs here is that this token's `expiry` **is** the maximum-session-lifetime bound `US-C10-14` requires, fixed at issuance from validated configuration (`T-C10-56`) and never extended afterward, which this ticket's TTL configuration already does — it only needed pointing at the right config key, named explicitly below.

## Scope

- `TokenIssuerPort` in `libs/identity-access/domain`: issue a token for a resolved identity, and verify/decode a presented token into its claims.
- `JwtTokenIssuer` in `libs/identity-access/infrastructure` over `@nestjs/jwt`, with signing secret/key and algorithm read through `ConfigService` and validated at boot; the token's TTL is the **maximum session lifetime** key from `T-C10-56`'s validated configuration — the same duration `US-C10-14` names as one of its two independent, device-bounded caps.
- Claim set: subject (user id), display name, role identifiers, issued-at, expiry. No session identifier, no credential, no hash, no permission list — permissions are resolved per request (`T-C10-39`).
- Jest tests: round-trip issue and verify, expired token rejected, tampered signature rejected, and the issued token's `expiry` equals `issuedAt + maxSessionLifetime` exactly, with no path that extends it after issuance (the negative test that proves this ticket does not reintroduce sliding).
- Out of scope: the guard that consumes it (`T-C10-28`), refresh tokens, which no `C10` story requires, and the inactivity bound, which is device-local and never reaches this adapter (`T-C10-58`).

## Acceptance criteria

**Given** a resolved identity **When** a token is issued **Then** its decoded claims carry the user identifier, display name, role identifiers and an expiry, and nothing else.

**Given** the configured maximum session lifetime **When** a token is issued **Then** its `expiry` claim equals `issuedAt + maxSessionLifetime`, and no operation anywhere in this adapter can extend an already-issued token's expiry — there is no method to call.

**Given** a token whose expiry has passed **When** it is verified **Then** verification fails with a typed error distinguishable from a signature failure.

**Given** a token whose payload has been altered **When** it is verified **Then** verification fails.

**Given** the signing configuration absent **When** the application boots **Then** it fails fast rather than signing with a default or empty secret.

**Given** the `identity-access/application` library **When** it is grepped for `@nestjs/jwt` **Then** there is no match; only the infrastructure adapter imports it.
