# [C10] T-C10-44 · TypeORM persistence and migration for scope grants

## Context

The persisted half of `T-C10-43`: `US-C10-07` requires the grant to be persisted and explicit, and `US-C10-08` requires a league grant to resolve to its competition set **at evaluation time**, so a competition added to a league is included without any change to the actor grants.

**Correlative adjustment.** `T-C10-43` now declares `ScopeGrant.validPeriod` as a `DateTimeRange`, matching `DATA-MODEL.md` §6.3/§20.1's `valid_from` (`NOT NULL`) / `valid_to` (nullable) pair, its `ck_iam_competition_scope_validity` CHECK and its partial index `WHERE valid_to IS NULL`. This ticket maps that pair; it no longer has to invent it. It also changes what "unique on the triple" must mean: `DATA-MODEL.md` §6.3 describes the table as **append-only** — "superseding it inserts a new row" — which an absolute unique constraint on `(user, kind, target)` would make impossible the moment a grant is ever retired and reissued. The constraint must therefore be **partial**, scoped to active grants, mirroring `uq_iam_user_role_active` on the sibling `iam_user_role` table. Nothing else about this ticket's scope changes: no story in this epic retires a grant yet, so this ticket only has to make retirement *possible* at the schema level, not implement it.

**Second defect fixed here.** As first written, this ticket named the table `identity_access.scope_grant` — wrong on both axes, not just the schema prefix: `DATA-MODEL.md` §6.3/§20.1 names it `iam.iam_competition_scope`, a different entity name entirely, not merely `iam.scope_grant`. Fixed throughout below.

**Third defect, verified against `DATA-MODEL.md` §20.1's attribute table column by column, not against a name that merely sounded plausible.** This ticket's `subject`/`kind`/`target` were placeholders, and `target` was wrong in a way that loses behavior, not just a label: the canonical table has no single `target` column. It has `subject_type`, `scope_kind`, and **two** columns for the subject — `subject_external_id` (nullable) and `subject_label` (nullable, free-text fallback) — guarded by `ck_iam_competition_scope_subject`. Collapsing them into one `target` column would silently delete the R10/NFR-AVL-03 fallback (recording the affected subject by label when the SCMS lookup is unavailable), which is PRD-backed behavior, not a drafting convenience this ticket is free to drop. `T-C10-43` now models the domain side of this split (`subjectExternalId`/`subjectLabel`, at least one required); this ticket maps it. The uniqueness constraint the Architect has fixed in `DATA-MODEL.md` is more precise than assumed above, too: `subject_external_id` is nullable, and under PostgreSQL's default `NULLS DISTINCT`, a unique index built on the raw column would treat every label-only grant as distinct from every other — two live label-only grants for the same subject would both be accepted, and revoking one would leave the other live (`FR-IAM-03`, `NFR-SEC-02`). The constraint is therefore built on `COALESCE(subject_external_id, subject_label)`, which is load-bearing, not stylistic.

**Why this ticket now exceeds the 3h cap.** Three corrections have landed on the same migration in three passes: temporal validity, the table/column names, and the subject-reference split. Splitting them into separate tickets now would force three migrations touching one table, sharing one entity, one mapper and one integration-test harness that the first of them would have to build — an artificial dependency, not independent work — so the size stands and the reason is recorded here rather than split after the fact.

## Scope

- TypeORM entity, mapper and `TypeOrmScopeGrantRepository` in `libs/identity-access/infrastructure`.
- Migration creating `iam.iam_competition_scope` (`DATA-MODEL.md` §6.3/§20.1): `user_id`, `subject_type`, `scope_kind`, `subject_external_id varchar(100)` nullable, and `subject_label varchar(255)` nullable (the free-text fallback; **both** columns, never collapsed into one), `valid_from timestamptz NOT NULL` / `valid_to timestamptz NULL` mapped from `ScopeGrant.validPeriod`. Constraints: `ck_iam_competition_scope_subject` (`subject_external_id IS NOT NULL OR subject_label IS NOT NULL`); a CHECK equivalent to `ck_iam_competition_scope_validity` (`valid_to IS NULL OR valid_to > valid_from`); the partial unique constraint exactly as the Architect fixed it —
  ```sql
  uq_iam_competition_scope_active
  UNIQUE (user_id, subject_type, scope_kind, COALESCE(subject_external_id, subject_label))
  WHERE valid_to IS NULL
  ```
  (the `COALESCE` is required, not optional polish: `subject_external_id` is nullable, and under Postgres's default `NULLS DISTINCT` a unique index on the raw column would let two live label-only grants for the same triple coexist) — and a partial index on `(user_id, subject_type, subject_external_id) WHERE valid_to IS NULL` for the scoped-query fast path (`FR-IAM-03`, `NFR-SEC-02`). Primary-key default per the convention `T-C10-17` fixes (`DEFAULT uuidv7()`, `DATA-MODEL.md` §3.1/§3.1.1, ADR-012).
- The mapper constructs `ScopeGrant.validPeriod` via `DateTimeRange.openEndedFrom(valid_from)` when `valid_to` is `null`, and `DateTimeRange.between(valid_from, valid_to)` otherwise, and reconstructs the subject reference from whichever of `subject_external_id`/`subject_label` is present — the repository never invents a shape the domain did not declare, in either direction.
- The league-to-competition resolution implemented as a query executed per evaluation, not as a materialized snapshot on the grant.
- The grant-listing operation of `T-C10-43`'s port takes the evaluation instant and filters in the query (`valid_from <= instant AND (valid_to IS NULL OR valid_to > instant)`), so the partial index is actually exercised rather than filtered in memory after a full fetch.
- Integration tests against real PostgreSQL: adding a competition to a league between two evaluations; inserting a new grant for the same triple after the previous one's `valid_to` is set (proving the unique constraint is partial, not absolute); inserting a row with neither `subject_external_id` nor `subject_label` (rejected by the subject CHECK); and inserting a second live grant whose `subject_label` matches an existing live grant's `subject_label` for the same user/type/kind, both with `subject_external_id IS NULL` (rejected by the `COALESCE` constraint, proving two label-only grants cannot silently coexist).
- Out of scope: the predicates; any competition or league table, which this epic does not own; any operation that sets `valid_to` — no use case retires a grant yet (`T-C10-43`'s scope note).

## Acceptance criteria

**Given** the migration **When** it runs and is reverted **Then** `iam.iam_competition_scope` is created and removed cleanly, with `subject_external_id`, `subject_label`, `valid_from`, `valid_to`, both CHECK constraints, `uq_iam_competition_scope_active` and the partial index in place.

**Given** a row with neither `subject_external_id` nor `subject_label` set **When** it is inserted **Then** the database rejects it on `ck_iam_competition_scope_subject`.

**Given** the same active grant inserted twice (both rows with `valid_to IS NULL`, identical `user_id`/`subject_type`/`scope_kind`/`subject_external_id`) **When** the second insert executes **Then** the database rejects it on `uq_iam_competition_scope_active`.

**Given** two live, label-only grants (`subject_external_id IS NULL` on both) sharing the same `user_id`/`subject_type`/`scope_kind`/`subject_label` **When** the second is inserted **Then** it is rejected — the `COALESCE` in the constraint, not the raw nullable column, decides uniqueness.

**Given** a grant whose `valid_to` has been set, and a new grant for the same subject/kind/target **When** the new grant is inserted **Then** it succeeds, because the unique constraint applies only to active grants.

**Given** a row with `valid_to <= valid_from` **When** it is inserted **Then** the database rejects it on the validity CHECK.

**Given** a league grant **When** a competition is added to that league and the grant is resolved again **Then** the new competition appears in the resolved set with no write to the grant row.

**Given** the repository **When** it returns grants **Then** the caller receives domain `ScopeGrant` objects with a correctly reconstructed `validPeriod` and subject reference, never TypeORM entities.
