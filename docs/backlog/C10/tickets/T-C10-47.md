# [C10] T-C10-47 · `AssignRoleToUser` use case, idempotent and authorization-guarded

## Context

`US-C10-11` requires role assignment to be denied for a non-administrator **by any path**, using the predicate of `US-C10-05`, and to be idempotent: assigning a role a user already holds creates no duplicate assignment and emits no spurious change event.

**Defect fixed here.** As first written, this ticket persisted `granted_at` (`iam.iam_user_role`, `DATA-MODEL.md` §6.2/§20.1, `NOT NULL`, "set by the application through `ClockPort`" per §3.3) with no stated source for the instant — the same class of gap `T-C10-08`'s AC2 (`ADR-009`) exists to catch: a use case with a mandatory timestamp to write and no named clock ends up reaching for `new Date()`. Every sibling use-case ticket that writes a timestamp names `ClockPort` explicitly (`T-C10-25`, `T-C10-54`, `T-C10-65`); this one now does too.

## Scope

- `AssignRoleToUser` use case in `libs/identity-access/application`, taking the `Actor` from `T-C10-39`, the target user and the role identifier, and using `ClockPort` for the assignment's `granted_at` timestamp — never `new Date()`.
- Authorization through the `actor may assign roles` predicate of `T-C10-38`; denial raises `AuthorizationError` and persists nothing.
- Validation that the target user and the role exist; unknown role or unknown user raises a typed error distinct from a denial.
- Idempotence checked in the domain, backed by the unique constraint of `T-C10-36`.
- Jest unit tests against stubbed repositories: allowed assignment, denied assignment, repeat assignment, unknown role, unknown user.
- Out of scope: the HTTP adapter (`T-C10-48`), the events (`T-C10-54`), the step-up requirement, which is `US-C10-15` and blocked by finding **F16**.

## Acceptance criteria

**Given** an administrator actor and a target user without the role **When** the use case executes **Then** the assignment is persisted and the operation reports success.

**Given** a non-administrator actor **When** the use case is invoked by any path **Then** it is denied by the authorization predicate and nothing is persisted.

**Given** a role the target user already holds **When** the same role is assigned again **Then** the operation succeeds, no duplicate assignment is created and no change event is emitted.

**Given** an unknown role identifier or an unknown target user **When** the use case executes **Then** it raises a typed error distinguishable from an authorization denial.

**Given** the application library **When** it is inspected **Then** the use case reads no request state and depends only on ports and the `Actor`.

**Given** the application library's production source, excluding `*.spec.ts` **When** it is grepped for a bare `new Date()` — no arguments **Then** there is no match; the assignment's `granted_at` comes from `ClockPort`. Constructing an instant from a value already in hand (`new Date(x)`) is unrestricted and is not what this check looks for — a literal "no match anywhere" grep would fail on any spec building a fixture instant, which is not the defect this criterion targets (the same correction applied to `T-C10-09` and `T-C10-54`).
