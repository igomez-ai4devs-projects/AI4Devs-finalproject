# [C10] T-C10-54 · `RoleAssigned` and `RoleRevoked` domain events

## Context

`US-C10-13` requires every role assignment and revocation to be published as a domain event carrying the acting administrator, the target user, the role, the timestamp from `ClockPort` and the **previous and new role sets**, so entitlement changes cannot be made silently.

**Dependency, not scope:** persisting and rendering these events as audit entries belongs to `C18` (`FR-AUD-01`, `FR-AUD-02`) — finding **F5**. `C10` publishes; `C18` records. This ticket declares the event shape `C18` will subscribe to and stops there.

**Defect fixed here, before implementation.** AC4 as first written — *"grepped for `new Date(` … there is no match"* — is unsatisfiable by a domain library with a real test suite: a literal grep for the substring `new Date(` also catches every spec fixture built with `new Date(x)`, which is legitimate and unrelated to the system-clock read `ADR-009` actually bans. `T-C10-08`'s AC2 already drew the correct line — *"no `new Date()`"*, empty parentheses — and this criterion is corrected to match it before anyone runs into the same false failure `T-C10-09` did.

## Scope

- `RoleAssigned` and `RoleRevoked` event types in `libs/identity-access/domain`, both extending `DomainEvent` from `T-C10-09`.
- Payload, identical in shape for both: actor identity, target user, role identifier, previous role set, new role set, occurrence timestamp from `ClockPort`.
- Events are produced by the aggregate operation, so they cannot be constructed from a state the operation did not reach.
- Jest unit tests asserting payload completeness, immutability and clock sourcing.
- Out of scope: dispatch (`T-C10-55`), any subscriber, any audit entry, any audit screen — all `C18`.

## Acceptance criteria

**Given** a role assignment **When** the event is produced **Then** it carries the actor identity, the target user, the role, the `ClockPort` timestamp, and both the previous and the new role set.

**Given** a role revocation **When** the event is produced **Then** it carries the same shape.

**Given** either event **When** a caller attempts to mutate its payload **Then** the mutation has no effect.

**Given** the domain library's production source, excluding `*.spec.ts` **When** it is grepped for a bare `new Date()` — no arguments **Then** there is no match; both event types take their timestamp from `ClockPort`, never the system clock. Constructing an instant from a value already in hand (`new Date(x)`) is unrestricted and is not what this check looks for.

**Given** the two event types **When** they are compared **Then** their payload shapes are structurally identical, so one `C18` subscriber can handle both.
