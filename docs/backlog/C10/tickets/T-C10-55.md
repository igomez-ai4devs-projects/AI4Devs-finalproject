# [C10] T-C10-55 · Role events collected and handed to the dispatcher on commit

## Context

`US-C10-13` requires the event to be published **when the transaction commits**, requires a failing subscriber to leave the role change committed with the dispatch failure logged, and requires that a failed or denied role change emits nothing at all. `ARCHITECTURE.md` §9 and ADR-008 place the single in-process dispatcher in `apps/api` behind `EventPublisherPort`.

**Narrowed — finding H1.** As first written, this ticket built the dispatcher mechanism itself (subscriber-failure isolation, the whole of `EventPublisherPort`'s wiring), with every acceptance criterion phrased against `RoleAssigned`/`RoleRevoked`. That made it the epic's only source of post-commit dispatch with failure isolation, and role administration is not part of the first delivery slice — a slice that needs exactly this mechanism (`T-C1-07`'s `LogIncidentUseCase`) would have had to depend on a role-shaped ticket to get it, or rebuild it. The generic mechanism is extracted to `T-C10-73`; this ticket keeps only what is actually role-specific — collecting the two role events and handing them to that dispatcher on a successful commit — plus the two acceptance criteria that were never about the dispatch mechanism to begin with (the denial/idempotence emit-nothing rule).

**Dependency:** `T-C10-73` supplies the dispatcher and its failure isolation; this ticket does not rebuild it. `C18` supplies the subscriber that turns these events into audit entries (finding **F5**). This ticket delivers the publication side and is complete without that subscriber; the acceptance scenarios use a test subscriber.

## Scope

- The assignment and revocation use cases (`T-C10-47`, `T-C10-51`) collect `RoleAssigned`/`RoleRevoked` on the aggregate and hand them to `T-C10-73`'s dispatcher only on a successful commit — no dispatcher logic lives here, only this collection step.
- Jest unit tests for the collection step; the dispatch-and-failure-isolation behavior itself is proven once, generically, in `T-C10-73`, and is not re-proven here against role events.
- Out of scope: the dispatcher mechanism and its failure isolation (`T-C10-73`); the audit subscriber, persistence of events, retry policy beyond logging — `C18` owns the durable side.

## Acceptance criteria

**Given** a successful role assignment **When** the transaction commits **Then** `RoleAssigned` is handed to the dispatcher exactly once, after the commit.

**Given** a successful role revocation **When** the transaction commits **Then** `RoleRevoked` is handed to the dispatcher exactly once.

**Given** a role change that is denied by authorization or fails validation **When** the use case returns **Then** no `RoleAssigned` and no `RoleRevoked` event is emitted.

**Given** an idempotent repeat assignment **When** it completes **Then** no event is emitted, because nothing changed.
