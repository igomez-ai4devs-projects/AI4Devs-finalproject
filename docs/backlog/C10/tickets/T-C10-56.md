# [C10] T-C10-56 · Configurable inactivity window and maximum session lifetime, with fail-fast validation

## Context

`US-C10-14` requires **two independent, device-bounded caps** — an inactivity period and a maximum session lifetime — both read through `ConfigService` with a documented default, and both must fail boot fast if missing or not a positive duration.

Phase 1 (PRD §14.3) — finding **F9** is closed for `C10` this revision; the Product Owner has assigned every `FR-IAM-*` requirement a phase, and `FR-IAM-06` is Phase 1.

**Widened, not just re-phased.** As first written, this ticket configured only the inactivity window. `US-C10-14`'s rewrite makes explicit that the maximum lifetime is a second, independent bound (PRD §14.8: device-bounded termination, "with a bounded maximum session lifetime"), and `T-C10-26` now sources a token's `expiry` from exactly this value. Configuring only one of the two caps would leave the other with no validated source.

## Scope

- Inactivity-window key **and** maximum-session-lifetime key, both added to the validated configuration schema of `T-C10-04`, each typed as a positive duration with a documented default; the maximum lifetime is the value `T-C10-26` reads to set a token's `expiry`.
- A third key for the warning threshold consumed by `T-C10-58`.
- Boot-time rejection of an absent, zero, negative or non-numeric value for either duration, with a message naming the key.
- The inactivity window and warning threshold exposed to the client through an existing authenticated endpoint, so neither is duplicated as a client constant. The maximum lifetime is **not** exposed for the client to enforce — enforcement of that bound is already structural (the token stops verifying at its own `exp`), so exposing it would only invite a client-side "extend the session" affordance PRD §14.8 rules out.
- Out of scope: the inactivity enforcement itself, which is entirely device-local (`T-C10-58`); the maximum-lifetime enforcement, which is `T-C10-26`'s `exp` claim, not a check this ticket performs.

## Acceptance criteria

**Given** valid positive durations for both the inactivity window and the maximum lifetime **When** the application boots **Then** it starts and both values are available through `ConfigService`.

**Given** either key absent, zero, negative or non-numeric **When** the application boots **Then** it fails fast with a message naming that key, and does not start.

**Given** the configured values **When** the source is grepped for a hardcoded timeout literal **Then** there is no match outside the configuration schema defaults.

**Given** an authenticated client **When** it requests the session policy **Then** it receives the inactivity window and the warning threshold from the server; the maximum lifetime is not part of that response.
