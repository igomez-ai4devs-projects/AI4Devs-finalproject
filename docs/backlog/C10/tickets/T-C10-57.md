# [C10] T-C10-57 · Maximum session lifetime is the token's own expiry — no sliding, no server-tracked window

## Context

**Regenerated, not retired — same ID, a different mechanism.** As first written, this ticket extended the `Session` aggregate of `T-C10-24` with a last-activity timestamp touched on every request, sliding a server-held expiry window forward. `T-C10-24` is retired: `PRD` §14.8 forbids exactly this — a stored, per-request-updated record of session liveness. `US-C10-14`'s rewrite replaces "one sliding window" with **two independent, device-bounded caps**: an inactivity period, enforced entirely on the device (`T-C10-58`, no backend component at all), and a maximum session lifetime, which needs no sliding mechanism because it is fixed the instant the token is issued and never revisited.

This ticket's remaining job is narrow: prove that the maximum-lifetime bound is exactly the token's `exp` claim (`T-C10-26`, sourced from `T-C10-56`'s configuration) and, just as importantly, prove that **nothing** in the backend extends it after issuance — the negative test that stands in for the sliding-window test this ticket used to need, and now exists specifically to catch a regression back toward the design PRD §14.8 rejects.

## Scope

- No aggregate change, no repository, no guard change — `T-C10-26` already issues the token with `expiry = issuedAt + maxSessionLifetime` (`T-C10-56`); this ticket's job is the regression test that keeps it that way.
- Integration test: issue a token, make several authenticated requests before the configured maximum lifetime elapses, then decode the token again — its `exp` claim is byte-identical to the value at issuance. No request, however many are made, changes it.
- Integration test: a token presented after its `exp` has passed is rejected by the standing global guard (`T-C10-28`) with `401` — proving the bound actually bites, through the ordinary expiry check, with no session-specific code path.
- Jest unit test with `FixedClock`: the maximum-lifetime boundary itself (at, just below, just above) is a property of `T-C10-26`'s issuance logic, covered there; this ticket does not duplicate it, only proves nothing downstream disturbs it.
- Out of scope: configuration (`T-C10-56`); the client warning (`T-C10-58`); the inactivity bound, which never reaches the backend.

## Acceptance criteria

**Given** a token issued with the configured maximum session lifetime **When** several authenticated requests are made before that lifetime elapses **Then** the token's `exp` claim is unchanged by every one of them — decoding it after N requests yields the same value as decoding it right after issuance.

**Given** that same token presented after its `exp` has passed **When** any protected route is called **Then** the request is rejected with `401` by the ordinary expiry check in `T-C10-28`, with no session record consulted, because none exists.

**Given** the backend source **When** it is inspected for any mechanism that recomputes, refreshes or slides an already-issued token's expiry **Then** there is none — this is the criterion that makes the retirement of `T-C10-24`'s sliding-window mechanism provable, not just asserted in prose.
