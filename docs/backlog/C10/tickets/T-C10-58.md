# [C10] T-C10-58 · Web inactivity warning with a stay-signed-in action, entirely on the device

## Context

`US-C10-14` requires the web client to warn the agent when the remaining time before either device-bounded cap crosses a threshold, offering an explicit **stay signed in** action, and requires that losing access mid-form does not silently discard entered data.

**Regenerated: the inactivity bound has no server component at all.** As first written, "stay signed in" issued "a lightweight authenticated request to slide the window server-side" — the server-tracked window `T-C10-24` held. That window is retired; PRD §14.8 places inactivity enforcement entirely **on the device**. The client now owns the whole inactivity timer: it is the only thing that knows how long the device has been idle, and "stay signed in" simply resets that local timer — no request is needed for it to do so. The **maximum lifetime** cap is different: it is the token's own `exp` (`T-C10-26`), fixed at issuance, and no client action — "stay signed in" or otherwise — can extend it. When the maximum lifetime elapses, the next authenticated request genuinely does fail with `401` (the ordinary expiry check), and *that* is where a real server response enters this story; inactivity alone never does.

## Scope

- Client-side idle timer driven by the inactivity window and threshold served by `T-C10-56`, running entirely on the device — no server call to start it, extend it or check it.
- Warning overlay from `T-C10-14` with a **stay signed in** action that resets the local idle timer (no HTTP call) and a sign-out-now action (`T-C10-34`).
- When the idle timer itself elapses with no response, the client enforces the inactivity bound locally: it clears its own auth state and routes to sign-in, exactly as `T-C10-34`'s sign-out does — inactivity termination *is* a client-triggered sign-out, not a distinct backend outcome.
- Separately, if the **maximum lifetime** elapses while the user is active, the next API call gets a real `401` from `T-C10-28`; the interceptor of `T-C10-30` already routes that to sign-in — this ticket's only job for that case is showing the same localized warning as the remaining time approaches that boundary too, computed from `issuedAt + maxSessionLifetime` held client-side from the token's own claims, not from a second server round-trip.
- The warning is announced assertively through the `aria-live` announcer and receives focus, so it is not missed by a screen-reader user.
- Form-data preservation: on either bound ending access, in-progress form state is retained locally and restored after re-authentication, and the user is told this has happened.
- Localized through Transloco; Jest component tests for the warning, the local-timer reset, the maximum-lifetime warning, and the restoration.
- Out of scope: the maximum-lifetime enforcement itself, which is `T-C10-26`'s `exp` claim plus the standing guard (`T-C10-28`), not new logic here.

## Acceptance criteria

**Given** the device idle for longer than the configured inactivity period **When** the threshold is crossed **Then** the client shows a localized warning with an explicit stay-signed-in action, computed and enforced entirely on the device.

**Given** that warning, from inactivity **When** the user chooses stay signed in **Then** the local idle timer resets with **no HTTP request**, and the warning closes.

**Given** the user does not respond to the inactivity warning **When** the idle timer elapses **Then** the client itself clears its auth state and routes to sign-in — the same action `T-C10-34` performs for a deliberate sign-out, triggered here by the timer instead of the user.

**Given** the maximum session lifetime approaching instead **When** its own warning threshold is crossed **Then** the client shows the equivalent warning, but "stay signed in" cannot extend this bound — if the user keeps working past it, the next request genuinely fails with `401` and the shell routes to sign-in through the ordinary interceptor path.

**Given** a form with entered data **When** either bound ends access **Then** the entered data is not silently discarded; it is retained and restored after re-authentication, and the user is told so.

**Given** the warning overlay **When** it opens **Then** it is announced assertively and receives focus, and focus returns to the previous element when it closes.
