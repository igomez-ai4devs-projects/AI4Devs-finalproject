# [C10] T-C10-60 · Re-authentication proves only the current attempt — per-request credential check, nothing stored

## Context

`US-C10-15` (retitled) requires a privileged operation invoked without proof of identity **for this attempt** to be refused with a **distinct, machine-readable** re-authentication-required outcome — not a generic `403` — with nothing persisted; and, once credentials are re-entered, requires that same original operation to succeed on retry. Crucially, the story now states the property this ticket was previously missing: *"proof given for the first action does not stand in for proof of the second, because the requirement is proof 'at the moment of the action', not proof for a stretch of time that follows it."*

**Redesigned, same ID.** As first written, this ticket evaluated a stored `isStepUpValid(window, now)` flag and, on success, "marked the session step-up-verified with a `ClockPort` timestamp" for reuse by later requests — precisely the "proof-once-then-trusted for a configured window" behavior the rewritten story rules out, and it depended on `T-C10-24`'s retired `Session` aggregate to hold the mark. There is no window and nothing is marked anywhere in this version: every privileged request re-proves identity for itself, and the check is stateless from one call to the next.

## Scope

- A `StepUpCredential` shape (subject's password, or whatever `IdentityProviderPort` accepts) added to `libs/shared/contracts`, carried **on the privileged request itself** — a field on that request's DTO, not a separate call and not a header tied to any stored context.
- Enforcement in the application layer: before executing a use case marked `@Privileged()` (`T-C10-59`), verify the credential presented **with this request** through `IdentityProviderPort`. Missing or invalid → raise a typed `ReauthenticationRequired` error and persist nothing; the use case never runs. Valid → the use case proceeds; nothing is written anywhere to remember that it did.
- A failed check leaves the actor's ordinary session and non-privileged access completely unaffected — it is a property of this one call, not a state change — and the attempt is logged.
- Exception-filter mapping of `ReauthenticationRequired` to a distinct status and error code, separate from `FORBIDDEN`, so a client can tell "not allowed" apart from "prove it again."
- Jest unit tests plus API-E2E scenarios for: refuse with no credential, refuse with an invalid credential, succeed with a valid one, and — the regression guard for the defect this ticket fixes — a second privileged call immediately after a successful first one is refused again unless it, too, carries a valid credential.
- Out of scope: the prompt UI (`T-C10-61`); the remaining `NFR-SEC-06` judgment call (finding **F16**).

## Acceptance criteria

**Given** a declared privileged operation invoked with no re-authentication credential on the request **When** it is invoked **Then** it is refused with the distinct machine-readable re-authentication-required outcome and nothing is persisted.

**Given** that refusal **When** the administrator retries the same operation with a valid credential attached to the retried request **Then** the operation is authorized for this attempt and succeeds.

**Given** a privileged operation just authorized this way **When** the administrator invokes a **second**, later privileged operation with no credential attached to it **Then** that second call is refused exactly like the first — proof given for the first call does not carry over, because nothing was stored to carry it.

**Given** an invalid credential submitted with a privileged request **When** it is checked **Then** the actor's ordinary session and non-privileged access are unaffected, the privileged operation is not authorized, and the attempt is logged.

**Given** the refusal outcome and an authorization denial **When** both are returned **Then** they carry different error codes, so a client can tell them apart without parsing a message.

**Given** the application library **When** it is inspected for any field, table or cache that survives past one request to record that identity was proven **Then** there is none — this is the criterion that makes the retirement of the stored step-up mark provable, not just asserted in prose.
