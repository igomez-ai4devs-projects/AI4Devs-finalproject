# [C10] T-C10-70 · `typecheck` target for library projects — close the CI gap on layer purity

## Context

Foundation work with no user story behind it. Source: `docs/product/ARCHITECTURE.md` §5.5, which requires `"types": []` in the `tsconfig.lib.json` of every `type:domain`, `type:application`, `type:contracts` and `type:util` library so `process`, `Buffer`, `fs` and `setTimeout` do not even compile in layers the dependency rule (§3) bans I/O from; and §12.3, which documents the limit rather than selling it as resolved: *"with `--bundler=none` a library has no `build` target and Jest compiles through `tsconfig.spec.json`, so no target in the workspace currently typechecks a library's `tsconfig.lib.json`. The setting therefore holds in the editor and in review, not in CI. Closing that gap — adding a `typecheck` target for library projects — is a known follow-up, worth doing before the first context hexagon makes the blind spot expensive."*

Verified against the one library that exists: `nx show project shared-util` lists exactly `lint` and `test` — no `build`, no `typecheck`. `libs/shared/util/tsconfig.lib.json` already carries `"types": []` (`T-C10-07`), so the policy is correctly authored; it simply has no compiler ever reading it outside an editor or a manual review.

This is a coverage gap, not a design change: it adds a check, it does not alter what §5.5 already requires. It should land before or alongside the next backend library ticket (`T-C10-08`, `libs/shared/domain`) so purity is CI-enforced from the first context-bearing library onward, rather than retrofitted later across a dozen libraries — the cost §5.5 itself warns about.

## Scope

- Add a mechanism that gives every `type:domain`, `type:application`, `type:contracts` and `type:util` library a `typecheck` target automatically, without a hand-added target block per project — prefer an Nx plugin registered in `nx.json` (target inference matching those tags or matching `tsconfig.lib.json` presence) over a manually maintained target per library, so the next library ticket (`T-C10-08` onward) inherits it for free. The target runs a no-emit typecheck (`tsc --noEmit` or equivalent) against that project's `tsconfig.lib.json`, never `tsconfig.spec.json`.
- Retrofit `libs/shared/util` — the only library that exists today — so `nx show project shared-util` lists `typecheck` alongside `lint` and `test`.
- Wire the new target into the CI gate so the enforcement is real, not local-only: `typecheck` joins the set `pnpm nx run-many` already runs in `.github/workflows/deploy-stage.yml` (today `-t lint test build`). Editing that workflow file is this ticket's scope to specify, not to implement here — `ci-cd-expert` owns `.github/workflows/` per `CLAUDE.md` §5.
- Out of scope: `type:infrastructure` libraries and the two applications — §5.5 keeps `"types": ["node"]` there deliberately, they are the I/O layers. Angular libraries — §5.5 generates them without a `types` entry, so there is nothing to gate. Widening the purity check beyond `process`/`Buffer`/`fs`/`setTimeout` or beyond the four listed library types — this ticket closes the enforcement gap §12.3 already names, it does not expand the policy.

## Acceptance criteria

Mechanical checks — this ticket has no user scenario.

**Given** the workspace **When** `pnpm nx show project shared-util` runs **Then** it lists a `typecheck` target in addition to `lint` and `test`.

**Given** `libs/shared/util/tsconfig.lib.json` carrying `"types": []` **When** a probe statement referencing `process.env` or `Buffer` is temporarily added to a file under `libs/shared/util/src` **Then** `pnpm nx typecheck shared-util` fails to compile; the probe is reverted before the ticket is closed.

**Given** the same probe reverted **When** `pnpm nx typecheck shared-util` runs **Then** it passes, and `pnpm nx test shared-util` is unaffected — the new target reads `tsconfig.lib.json` only, never `tsconfig.spec.json`.

**Given** `.github/workflows/deploy-stage.yml` **When** it is inspected **Then** its `pnpm nx run-many` invocation includes `typecheck` for library projects, so the gate that today only bites in the editor and in review also bites in CI.

**Given** any future library generated per `ARCHITECTURE.md` §5.5 as `type:domain`, `type:application`, `type:contracts` or `type:util` **When** it is scaffolded with no further target configuration **Then** it already carries a working `typecheck` target — proving the mechanism is inference-based, not a per-project addition someone can forget.
