# [C10] T-C10-71 · Mechanical cross-check of `DATA-MODEL.md` constraint and index identifiers

## Context

Foundation work with no user story behind it. Source: an Architect finding surfaced while resolving the `T-C10-43`/`T-C10-44` column-drift defect, relayed here for ticketing — not invented by this role. `docs/product/DATA-MODEL.md` states every constraint and index identifier (`uq_`, `ix_`, `ck_`, `pk_`, `fk_`) in up to **three** places — the per-context narrative (§5–§15), the cross-cutting indexes catalog (§16), and the entity-level attribute dictionary (§20) — and nothing checks that the three copies agree. The Architect measured **45 such identifiers living in two or more locations, with zero mechanical verification**, and today's session found two real drifts in a single turn: `uq_sla_policy_scope` kept its old shape in the narrative after the dictionary copy gained `NULLS NOT DISTINCT`, delivering the non-biting form of the constraint to whoever writes a ticket from the narrative (the narrative is the copy a ticket-writer reads); and `ix_iam_user_role_active` was spelled two different ways on the exact sibling table `T-C10-44`'s new constraint was modeled on. Neither was caught by anything mechanical — only by two people happening to read both copies at once, which does not scale as `DATA-MODEL.md` grows past this epic.

This is documentation-integrity tooling, not a schema change: it changes nothing about what `DATA-MODEL.md` says, only whether a future drift between its own copies is caught before it reaches a ticket. It sits with the scaffolding steps `DATA-MODEL.md` §19 already lists as the concrete next steps toward a real workspace — a natural sibling to `T-C10-70`'s `typecheck` gate: both close a "written correctly once, never checked again" gap the Architect named explicitly rather than selling as resolved.

## Scope

- A script, `tools/data-model-probes/verify.mjs` — same location convention as `tools/boundary-probes/verify.mjs` (`T-C10-03`) — that parses `docs/product/DATA-MODEL.md`, extracts every identifier matching `(uq|ix|ck|pk|fk)_[a-z0-9_]+` together with its stated definition (the constraint expression, the indexed columns and any `WHERE`/`NULLS` clause) from each of the three sections it can appear in, and groups occurrences by identifier.
- For every identifier appearing in **two or more** locations, assert the definitions are identical after normalizing only whitespace and backtick/markdown formatting — no semantic interpretation, so the check cannot be fooled by "close enough" prose drift.
- On success, print a summary: how many identifiers were found in total, how many were cross-checked (appeared more than once), and that all matched. No hard-coded expected count — `DATA-MODEL.md` will grow, and a magic number would make this check's own maintenance a source of false failures.
- On a mismatch, exit non-zero and print the identifier, the conflicting locations (section + a short excerpt of each definition), so the failure is actionable without re-reading the whole document.
- A `pnpm` script entry, `verify:data-model`, alongside the existing `verify:boundaries` in `package.json`.
- Wired into the CI gate: added to the same `pnpm nx run-many`/workflow step `T-C10-70` extends with `typecheck`, or its own step — either way, the check must run in CI, not only locally.
- Out of scope: fixing any drift the check would find in `DATA-MODEL.md` as it stands — the two drifts named above are the Architect's to fix in the document itself, not this ticket's to correct; this ticket only builds the detector. Also out of scope: checking anything other than the five listed identifier prefixes (no table names, no column names, no FR/NFR identifiers — those are different problems with different shapes).

## Acceptance criteria

Mechanical checks — this ticket has no user scenario.

**Given** `docs/product/DATA-MODEL.md` as it stands when this ticket is implemented **When** `pnpm verify:data-model` runs **Then** it exits `0` and reports how many identifiers were scanned and how many were cross-checked.

**Given** a deliberately mismatched copy of one already-consistent identifier — introduced as a probe, mirroring either real drift found today (a changed clause in one copy, or a renamed identifier in one copy only) **When** the check runs **Then** it exits non-zero and names the exact identifier and the two locations that disagree; the probe is reverted before the ticket is closed, exactly as `tools/boundary-probes/verify.mjs` (`T-C10-03`) reverts its own probes.

**Given** an identifier that legitimately appears only once in the whole document **When** the check runs **Then** it is not flagged — the check compares copies against each other, it does not require every identifier to be repeated.

**Given** the CI workflow **When** it is inspected **Then** `verify:data-model` (or the `nx run-many` target that wraps it) runs as part of the pipeline, not only as a local script.

**Given** the script's source **When** it is inspected **Then** it reads `docs/product/DATA-MODEL.md` only — it does not parse or depend on the backlog, the tickets, or any generated schema, because its job is internal consistency of one document, not conformance of anything else to it.
