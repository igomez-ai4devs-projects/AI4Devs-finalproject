# [C10] T-C10-72 · Bootstrap seed — the first System Administrator and the first Requester

## Context

Foundation work with no user story behind it. Source: a gap the Product Owner found while cutting the delivery slices — verified against the ticket set, not this backlog's own claim: no ticket in this epic inserts a single row into `iam.iam_user`. `T-C10-36` seeds the eight roles; nothing seeds an account to hold one. Without this, `US-C10-01` (sign in) has no credential that can ever succeed, which makes the entire epic — not only the first delivery slice — undemonstrable end to end: every acceptance scenario that starts with "given a registered user" is unrunnable against a freshly migrated database.

**Scope decided, not re-opened.** Creating an account is a **product capability** — `FR-SRQ-09`, owned by `C2`, not drilled into any delivery slice yet. What is missing here is narrower: a one-time infrastructure bootstrap so a database that has only ever run migrations has *someone* to sign in as. This ticket is an idempotent seed migration, not a `CreateUser` use case, and it must not grow into one. If implementing it reveals that a migration genuinely cannot satisfy what a slice needs (for example because a screen needs to *create* the second and third user, not just find two already seeded), that is a scope gap to report, not a license to add a use case here.

Sequenced after `T-C10-21` (creates `iam.iam_user`) and `T-C10-36` (seeds the role rows this ticket assigns) — both prerequisite infrastructure that exists regardless of which delivery slice is being built, the same bucket `T-C10-01`–`T-C10-15` are already in.

**Not part of delivery slice 1 — corrected after first being pulled in by this ticket's own UUID design.** This ticket was briefly scheduled into slice 1 because its seeded Requester row needed a fixed, citable id for `T-C10-74`'s disposable `Actor` to point at. That reasoning about the *id* was right; scheduling the *whole seed migration* into the slice was not: with authentication deferred in that slice, nothing reads `iam.iam_user` at all — `Incident.reporter_user_id` is a **soft reference** with no foreign key (`DATA-MODEL.md` §20, line 2446), so the row this ticket would insert is never queried, never joined, never checked. Two seeded accounts nobody reads buy the slice nothing. This ticket ships later, with the rest of the identity stack (block B), not in slice 1.

**The Requester's row id is still a fixed, known constant — the ownership just starts elsewhere.** `T-C10-74` (delivery slice 1's disposable `Actor` provider, which *is* in the slice and needs the id now) declares `BOOTSTRAP_REQUESTER_ID` first, in `apps/api/src/bootstrap/bootstrap-identities.ts` (or the equivalent single location). **When this ticket is implemented, it takes over:** it declares the constant in its own migration file and uses it — not a fresh `uuidv7()` — as the Requester row's explicit primary key; `T-C10-74`'s file is updated in the same change to import it from here instead. This is the one deliberate, documented exception to the `DEFAULT uuidv7()` convention `T-C10-17` fixes — a bootstrap identity an earlier, disposable ticket had to cite by name before this one existed, not a precedent for any other row in this schema. The System Administrator row keeps a generated id — nothing needs to know it in advance.

## Scope

- A seed migration inserting exactly two `iam.iam_user` rows: one System Administrator (generated id, per the standing convention) and one Requester (**fixed id** — takes over the `BOOTSTRAP_REQUESTER_ID` constant `T-C10-74` declared first, not `uuidv7()`; update `T-C10-74` in the same change to import it instead).
- Both accounts' credentials come from validated configuration — two new environment variables per account (e.g. an email/identifier and a password) — read and bcrypt-hashed **at migration time**; no literal password ever appears in the migration source or in version control. Consistent with `T-C10-16`'s fail-fast convention, the migration refuses to run if either pair is absent, rather than falling back to a known default credential.
- A matching `iam.iam_user_role` row for each account, assigning the seeded System Administrator and Requester roles from `T-C10-36`.
- Idempotent on re-run: a second run neither duplicates the accounts nor fails, matching the pattern `T-C10-36`'s own role seed already uses.
- Out of scope: any use case for creating a user (that is `FR-SRQ-09`, `C2`, not drilled here); any password-reset or credential-rotation path for the seeded accounts; seeding any account beyond these two.

## Acceptance criteria

Mechanical checks — this ticket has no user scenario.

**Given** a freshly migrated database **When** the migration chain has run **Then** `iam.iam_user` holds exactly two additional rows beyond whatever `T-C10-21`'s own migration leaves — one System Administrator, one Requester — each with a bcrypt-hashed password and a role assignment in `iam.iam_user_role` matching its intended role from `T-C10-36`.

**Given** either bootstrap credential environment variable absent **When** the migration runs **Then** it fails fast, naming the missing variable, rather than seeding an account with a default or empty credential.

**Given** the seed migration **When** it is run a second time **Then** it does not duplicate either account and does not fail.

**Given** the seeded System Administrator's credentials **When** they are submitted to the sign-in endpoint (`T-C10-27`) **Then** authentication succeeds and the returned token's role claim matches the System Administrator role — the first end-to-end proof that `US-C10-01` is runnable against a migrated-only database.

**Given** the migration **When** it is reverted **Then** both seeded rows and their role assignments are removed cleanly, and the revert is repeatable.

**Given** the Requester row's `id` column **When** it is read back after the migration runs **Then** it equals `BOOTSTRAP_REQUESTER_ID` exactly, and grepping the codebase for that same literal UUID finds it declared in exactly one place — this migration, which now owns the constant — with `T-C10-74` updated in the same change to import it rather than declare its own copy.
