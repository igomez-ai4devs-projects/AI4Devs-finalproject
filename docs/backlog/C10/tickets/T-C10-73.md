# [C10] T-C10-73 · Generic post-commit event dispatcher, extracted from `T-C10-55`

## Context

Foundation work with no user story behind it. Source: finding **H1**, raised by the Product Owner while cutting the delivery slices and verified here: `T-C10-55` builds the **only** post-commit dispatcher with subscriber-failure isolation in this epic, but its five acceptance criteria are written entirely against `RoleAssigned`/`RoleRevoked` — role events that are not part of the first delivery slice. `T-C1-07`'s own AC3 (*"Given a subscriber that throws when handling `IncidentLogged`… Then the Incident remains persisted and the failure is isolated to the subscriber"*) needs exactly this mechanism and cannot get it from a ticket scoped to role administration.

This ticket extracts the mechanism `T-C10-55` never should have owned exclusively: `EventPublisherPort` (`T-C10-09`) bound to a single in-process dispatcher in `apps/api`, invoked after commit, isolating a failing subscriber from the caller and the transaction — generic over `DomainEvent`, with no role vocabulary anywhere in it. `T-C10-55` keeps only what is actually role-specific: wiring the assignment/revocation use cases to collect their events and hand them to this dispatcher, plus the two role-event-shaped acceptance criteria that were never about the dispatch mechanism itself.

## Scope

- The in-process dispatcher in `apps/api`, bound to `EventPublisherPort` from `T-C10-09`, invoked strictly after commit, never inside the transaction — generic over any `DomainEvent` subtype.
- Subscriber-failure isolation: a subscriber that throws is caught, logged with the correlation identifier, and never propagated into the caller or the transaction.
- A registration seam so any use case (`T-C1-07`'s `LogIncidentUseCase`, `T-C10-55`'s role use cases, and every later one) can register a subscriber against an event type without this ticket knowing what that type is.
- Jest unit tests plus an API-E2E scenario using a **generic** deliberately-failing test subscriber and a generic test event — not `RoleAssigned`, so the mechanism is proven independently of any one consumer.
- Out of scope: any specific event type, any specific use case's own collect-and-publish wiring (each consumer's own ticket owns that — see `T-C10-55`, `T-C1-07`), the durable/audit side of any event (`C18`).

## Acceptance criteria

Mechanical checks — this ticket has no user scenario.

**Given** a generic test event published by a use case **When** its transaction commits **Then** the event is dispatched exactly once, strictly after the commit.

**Given** a subscriber registered against that event type that throws **When** the event is dispatched **Then** the triggering use case's own outcome is unaffected, the caller receives success, and the dispatch failure is logged with the correlation identifier.

**Given** a use case whose transaction is rolled back **When** it fails **Then** no event reaches any subscriber — publication never happens ahead of, or independently of, the commit it is conditioned on.

**Given** the dispatcher's source **When** it is inspected **Then** it contains no vocabulary specific to `identity-access`, `RoleAssigned` or `RoleRevoked` — every reference above is generic, so `T-C10-55` and `T-C1-07` can both depend on this ticket without importing each other's context.
