# [C10] T-C10-74 · Fixed `Actor` provider for delivery slice 1 — disposable

## Context

Foundation work with no user story behind it. Source: the Product Owner's minimal cut of delivery slice 1 ("register an Incident and see it, as simply as possible"), approved by the user: authentication is out of this slice entirely — not even a fixed-user *sign-in*, a fixed `Actor` supplied directly at the composition root for every request. `T-C1-07`'s `LogIncidentUseCase` already receives its `Actor` as a parameter and is unmodified by this decision; only what supplies that parameter changes for now.

**This ticket is disposable — see `disposable: true` above.** `T-C10-39` ("`Actor` assembly with per-request server-side permission resolution") is the ticket that deletes it: the day a real per-request resolver exists, this class is removed outright, not refactored into it. Nothing outside this one class may come to depend on it existing, or `T-C10-39` will have to work around a dependency it should simply be replacing.

**This ticket owns `BOOTSTRAP_REQUESTER_ID` — for now.** `T-C10-72` (the seed migration that would otherwise own this constant, since it is the one that actually writes the row) does **not** ship in delivery slice 1: with authentication deferred, nothing reads `iam.iam_user`, `Incident.reporter_user_id` is a **soft reference** with no foreign key (`DATA-MODEL.md` §20, line 2446), and seeding two accounts nobody queries buys this slice nothing. `T-C10-72` ships later, "with the identity stack" (see its own `## Context`). Until then, this ticket is the *only* consumer of the constant, so this ticket declares it — not `T-C10-72`, which does not exist yet in this slice's build order.

**Ownership transfers to `T-C10-72` the day it is implemented, not before.** When `T-C10-72` lands, it becomes the row's actual writer and takes over the constant: it declares `BOOTSTRAP_REQUESTER_ID` in its own migration, and **this ticket's file must be updated** to import it from there instead of declaring it locally. Whoever implements `T-C10-72` is responsible for making that edit here too — it is one line in each file, but skipping it leaves two independent declarations of the same literal, exactly the drift this design exists to prevent. `T-C10-72`'s own `## Context` states the same transfer, so either ticket read alone tells the same story.

## Scope

- One class in `apps/api`'s composition root — no other library, and nothing in `type:domain`, `type:application` or `type:contracts` may import or know about it. It constructs a fixed `Actor` value and supplies it wherever this slice's use cases currently expect one to be resolved.
- The exported constant `BOOTSTRAP_REQUESTER_ID`, declared in `apps/api/src/bootstrap/bootstrap-identities.ts` (or the equivalent single location) **by this ticket**, for as long as `T-C10-72` has not shipped. The fixed `Actor`'s user identifier is this constant, never a second literal typed independently.
- No permission-checking logic here beyond whatever the fixed `Actor` already carries as a static, hardcoded value sufficient for `T-C1-07` to authorize a Requester logging an Incident — this class does not consult any Role/Permission table, because none is seeded in this slice.
- Out of scope: any sign-in flow, any token, any guard; any change to `T-C1-07`'s signature or to any other use case's signature; the real resolver (`T-C10-39`); actually seeding a matching `iam.iam_user` row — nothing reads one yet, and that seeding is `T-C10-72`'s job on its own schedule, not this ticket's to pull forward.

## Acceptance criteria

Mechanical checks — this ticket has no user scenario.

**Given** the composition root **When** it is inspected **Then** exactly one class constructs the fixed `Actor`, and no `type:domain`, `type:application` or `type:contracts` project imports or references it.

**Given** the constant this ticket declares **When** the codebase is grepped for the literal UUID value **Then** it appears in exactly one place — this ticket's own declaration — for as long as `T-C10-72` has not shipped.

**Given** `T-C1-07` **When** it executes against this fixed `Actor` **Then** it authorizes and persists exactly as it would against any resolved `Actor`, with no change to its own file.

**Given** `T-C10-72` shipping **When** it is implemented **Then** this ticket's file is updated in the same change to import `BOOTSTRAP_REQUESTER_ID` from `T-C10-72` instead of declaring it, so the constant has exactly one owner at every point in time, never zero and never two.

**Given** this ticket's file **When** `T-C10-39` is implemented **Then** this class is deleted outright, not adapted — its own `## Context` names `T-C10-39` for exactly this reason.
