# [C10] T-C10-75 · `PERSISTENCE_MODE` configuration switch and the data-source CLI guard

## Context

Foundation work with no user story behind it. Source: **ADR-015** (`docs/product/ARCHITECTURE.md` §10, "Stage prototype on Render: two services, no database, a configuration-selected in-memory persistence adapter"), decision 1 — the Product Owner's explicit constraint that the Render prototype ships with **no database** and Incidents **kept in memory**, proven end to end without touching `DATA-MODEL.md`, the PRD or any boundary rule.

`apps/api/src/config/env.validation.ts` (`T-C10-16`) today makes `POSTGRES_HOST`/`PORT`/`DB`/`USER`/`PASSWORD` unconditionally mandatory, and `apps/api/src/data-source.ts` — the TypeORM CLI entry point — always builds a PostgreSQL `DataSource`. Neither can run on Render's `sport-itsm-api` service, which sets no `POSTGRES_*` variable at all. This ticket introduces the switch ADR-015 decision 1 specifies: `PERSISTENCE_MODE=postgres|memory`, mandatory, no default — "the file's own doctrine (every key mandatory, a missing key fails the boot). Choosing a non-durable store must be an explicit act of whoever configures the environment, never an inference."

**Must land in the same change as `T-C10-76`, or CI goes red.** The moment `PERSISTENCE_MODE` becomes a mandatory key with no default, every environment block that boots the API or the CLI needs it set — `api-e2e`'s targets, `incident-infrastructure`'s `integration` targets, both compose files, the pipeline workflow. `T-C10-76` (`ci-cd-expert`) adds it to all of those. Landing this ticket alone breaks every one of them at the next boot; landing `T-C10-76` alone is a no-op with nothing yet to read the new key. Neither is reviewable in isolation as "done" — merge them together. `depends_on` is listed both ways in these two tickets for that reason, not because one strictly builds on the other's code.

**No AppModule-booting spec left stranded.** `apps/api/src/testing/test-event-dispatch.harness-gating.spec.ts` boots a real `AppModule` under three `NODE_ENV` values with a hand-built `POSTGRES_*` fixture (lines ~20–30) that satisfies `env.validation.ts` today. This ticket adds `PERSISTENCE_MODE: 'postgres'` to that same fixture object — one line, no behavior change, since the spec already exercises the `postgres` path and must keep doing so (it proves the `NODE_ENV=test`-only dispatch route, nothing about persistence mode).

## Scope

- `PersistenceMode` enum (`postgres` | `memory`) and a new `PERSISTENCE_MODE: PersistenceMode` field on `EnvironmentVariables` (`apps/api/src/config/env.validation.ts`), validated with `@IsEnum`, mandatory, **no in-code default** — the same pattern `NODE_ENV`/`NodeEnvironment` already uses on that same class.
- `POSTGRES_HOST`/`POSTGRES_PORT`/`POSTGRES_DB`/`POSTGRES_USER`/`POSTGRES_PASSWORD` become conditionally required: `@ValidateIf((env) => env.PERSISTENCE_MODE === PersistenceMode.Postgres)` ahead of each existing decorator. In `memory` mode they are optional, and if present, ignored — no code path reads them in that mode.
- A cross-field safety rail: `PERSISTENCE_MODE === PersistenceMode.Memory && NODE_ENV === NodeEnvironment.Production` fails `validateEnvironment()` with a message naming both offending keys, checked after `validateSync()`'s per-property pass (there is no current production environment per ADR-013, so this rail costs nothing today and forecloses the worst case mechanically rather than by convention).
- `apps/api/src/data-source.ts` (the CLI entry point for `migration:generate`/`run`/`revert`/`show`) refuses to construct a `DataSource` and throws, naming `PERSISTENCE_MODE`, unless it reads `postgres` — running a migration command "in memory mode" is meaningless and must fail loudly, never silently try `localhost:5432`.
- `PERSISTENCE_MODE=postgres` added to `.env.example`, next to the `POSTGRES_*` block it now gates.
- `PERSISTENCE_MODE: 'postgres'` added to the `POSTGRES_*` fixture in `apps/api/src/testing/test-event-dispatch.harness-gating.spec.ts` — the only spec in this repository that boots a real `AppModule` today.
- Out of scope: the in-memory repository adapter itself (`T-C10-77`); the composition-root wiring that actually selects a binding set by mode (`T-C10-78`); every CI/Docker/`project.json` environment block (`T-C10-76`); any change to `apps/api/src/database/database.module.ts` or `buildDatabaseConnectionOptions()` beyond what already reads `POSTGRES_*` — those stay `postgres`-mode-only consumers, unaware of the new key.

## Acceptance criteria

Mechanical checks — this ticket has no user scenario.

**Given** `PERSISTENCE_MODE` absent from the environment **When** the application boots **Then** it fails fast naming `PERSISTENCE_MODE`, the same way a missing `NODE_ENV` does today.

**Given** `PERSISTENCE_MODE=postgres` and every `POSTGRES_*` key present and valid **When** the application boots **Then** it starts, exactly as before this ticket.

**Given** `PERSISTENCE_MODE=postgres` and any `POSTGRES_*` key missing **When** the application boots **Then** it fails fast naming that key — unchanged behavior from before this ticket.

**Given** `PERSISTENCE_MODE=memory` and no `POSTGRES_*` key set at all **When** the application boots **Then** validation passes (subject to the production rail below).

**Given** `PERSISTENCE_MODE=memory` and `NODE_ENV=production` **When** the application boots **Then** validation fails, naming both `PERSISTENCE_MODE` and `NODE_ENV`.

**Given** `apps/api/src/data-source.ts` **When** `pnpm typeorm migration:show -d apps/api/src/data-source.ts` runs with `PERSISTENCE_MODE=memory` in the environment **Then** it fails immediately with a message naming `PERSISTENCE_MODE`, before attempting any connection.

**Given** `apps/api/src/data-source.ts` **When** the same command runs with `PERSISTENCE_MODE=postgres` **Then** it behaves exactly as it did before this ticket.

**Given** `apps/api/src/testing/test-event-dispatch.harness-gating.spec.ts` **When** it is re-run after this ticket **Then** all three `NODE_ENV` scenarios still pass unchanged.

## Testing methodology (per story / feature)

Mechanical/config ticket: no Given/When/Then user scenario. Unit specs on `env.validation.ts` cover every branch above (enum present/absent, `@ValidateIf` in both modes, the production rail, each `POSTGRES_*` key). A short unit spec on `data-source.ts`'s guard proves it throws before any `DataSource` is constructed — mock or spy on `DataSource`'s constructor / `buildDatabaseConnectionOptions()` to prove it is never called in `memory` mode.

## Testing stack (for realistic recommendations)

**Jest 29.7** + `ts-jest`, run in the ordinary Nx `test` target (`apps/api`) — no PostgreSQL required for any of these specs, since they exercise validation logic and the CLI guard only, never a real connection.

## Implementation handoff (split by level)

Single-level change: `backend-engineer` edits `env.validation.ts`, `data-source.ts`, `.env.example` and the harness-gating spec's fixture in one pass, and writes the accompanying unit specs (`*.spec.ts`, co-located).
