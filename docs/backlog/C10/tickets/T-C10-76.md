# [C10] T-C10-76 · `PERSISTENCE_MODE` set across every environment block that boots the API or the CLI

## Context

Foundation work with no user story behind it. Source: **ADR-015** (`docs/product/ARCHITECTURE.md` §10), decision 1 and consequence 8: "`.env.example`, every in-repository environment block that boots the API or the CLI (`api-e2e` and `incident-infrastructure` targets, compose files, the workflow, specs that boot `AppModule`) gains `PERSISTENCE_MODE=postgres`; that is the price of the mandatory key and is paid once."

**Must land in the same change as `T-C10-75`, or CI goes red.** `T-C10-75` makes `PERSISTENCE_MODE` a mandatory, no-default key. Every place below already boots the API or the migration CLI against real PostgreSQL and must keep doing so unchanged — this ticket is pure configuration plumbing, adding one variable everywhere the mandatory-key doctrine now requires it, with **`postgres`** as the value everywhere except the one place that deliberately runs the prototype without a database. `T-C10-75`'s own `.env.example` and harness-gating-spec edits are **not** duplicated here — see that ticket's Scope for the split.

## Scope

Add `PERSISTENCE_MODE=postgres` to every one of the following (each already boots the API or the TypeORM CLI against a real PostgreSQL and must continue to):

- `apps/api-e2e/project.json` — the `env` blocks of the `e2e-migrate` and `serve-under-test` targets (both already carry the `POSTGRES_*`/`NODE_ENV`/`PORT` block this key joins).
- `libs/incident/infrastructure/project.json` — the `env` blocks of the `integration-migrate` and `integration` targets (same `POSTGRES_*` shape, same reasoning: `T-C1-06`'s round-trip integration spec boots against real PostgreSQL and must keep doing so).
- `docker/docker-compose.dev.yml` — the `api` service's `environment:` block.
- `docker/docker-compose.e2e.yml` — this file starts only the ephemeral `postgres-e2e` database service; it has no `api` service of its own to add the variable to. **No change needed here** — recorded so the omission reads as verified, not missed.
- `.github/workflows/deploy-stage.yml` — no `PERSISTENCE_MODE` occurrence needed in the `verify`/`acceptance` jobs themselves (they run through the Nx targets above, which now carry the variable at the target level); confirm this by re-reading the workflow after `T-C10-75`/`T-C10-76` land, and if any job step invokes `pnpm migration:run`/`pnpm typeorm …` directly with its own inline `env:` block (rather than through an Nx target's own `env`), add `PERSISTENCE_MODE=postgres` there too.

Add `PERSISTENCE_MODE=memory` to exactly one place — the stage prototype's own definition:

- `docker/docker-compose.stage.yml` — the `api` service's `environment:` block, alongside its existing `NODE_ENV=${NODE_ENV:-staging}` and `PORT=${PORT:-3300}` lines. This is a **local smoke-test convenience only** (this file's own header comment: Render itself sets service environment variables by hand in its dashboard, this file is not read by Render) — but it is also the one file in the repository that models the stage topology for a `docker compose up` dry run, so it must model the real value, not `postgres`.

**Found while touching `docker-compose.dev.yml` — reported, not fixed here.** The `api` service's `environment:` block in that file carries only `NODE_ENV`/`PORT` today; it has never carried `POSTGRES_HOST`/`PORT`/`DB`/`USER`/`PASSWORD`, even though `env.validation.ts` (`T-C10-16`) has required them unconditionally since before this ticket. `docker compose -f docker/docker-compose.dev.yml up api` therefore already fails environment validation today, independent of anything in this ticket or ADR-015 — a pre-existing gap between that compose file and `T-C10-16`'s own landing, not something ADR-015 introduces or this ticket is scoped to fix. Reported for `ci-cd-expert`'s own backlog; adding `PERSISTENCE_MODE=postgres` to that same (already-incomplete) block does not make it worse, and is done anyway per this ticket's Scope.

- Out of scope: `apps/api/src/config/env.validation.ts`, `apps/api/src/data-source.ts`, `.env.example` and the harness-gating spec (all `T-C10-75`); the in-memory adapter (`T-C10-77`); the composition-root wiring (`T-C10-78`); the nginx reverse proxy and `docker-compose.stage.yml`'s `web` service (`T-C10-79`); fixing the pre-existing `docker-compose.dev.yml` gap reported above.

## Manual configuration checklist (Render / GitHub) — full list, carried once for the whole Render-demo slice

This ticket touches no Render-dashboard setting directly, but it is the natural place to record the complete manual checklist the user will work through once `T-C10-75`, `T-C10-77`, `T-C10-78` and `T-C10-79` are all merged (referenced from each of those tickets rather than repeated in full there):

1. **GitHub Actions secrets** (repository settings → Secrets and variables → Actions): `RENDER_DEPLOY_HOOK_API` and `RENDER_DEPLOY_HOOK_WEB` — the deploy-stage job already reads both and is a no-op (skipped, not failing) until they exist (`.github/workflows/deploy-stage.yml`).
2. **`ghcr.io` pull credential on Render** — a Personal Access Token (classic) scoped to `read:packages` only, created under the GitHub account that owns the `ghcr.io/igomez-ai4devs-projects/*` images, registered in Render as a private registry credential so both services can pull `sport-itsm-api`/`sport-itsm-web`.
3. **Render service `sport-itsm-api`** — image-backed, one instance, autoscaling **off**; environment variables `NODE_ENV=staging`, `PORT=3300`, `PERSISTENCE_MODE=memory`; no `POSTGRES_*` variable set at all; empty pre-deploy command; no health-check path configured yet (`/health/live` does not exist — Render falls back to port detection until it does).
4. **Render service `sport-itsm-web`** — image-backed; environment variable `API_UPSTREAM_URL=https://<sport-itsm-api's-own-Render-URL>.onrender.com`; `PORT=80`; health check `/health` (served by nginx itself).
5. **First push to `main`** — `deploy-stage.yml`'s `deploy-stage` job runs only on a push to `main`, never a branch or PR; day-to-day work happens on `finalproject-IGR`, so nothing deploys until the user deliberately merges/pushes to `main`. Decide and execute that merge only once `T-C10-75`, `76`, `77`, `78` and `79` (and `T-C1-103`/`104`) are all in place — a partial deploy would ship a web image whose nginx has no `/api/` proxy yet, or an API that still expects PostgreSQL.
