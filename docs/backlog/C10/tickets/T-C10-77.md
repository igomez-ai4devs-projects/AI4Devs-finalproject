# [C10] T-C10-77 · `InMemoryIncidentRepository` — the in-memory Incident persistence adapter

## Context

Foundation work with no user story behind it. Source: **ADR-015** (`docs/product/ARCHITECTURE.md` §10), decision 2 — the second, non-durable adapter behind `IncidentRepositoryPort`/`IncidentReadRepositoryPort` that makes the Render prototype demonstrable with **no database on Render**.

**Placement, decided by ADR-015, not by this ticket.** An outbound adapter whose signatures name `Incident` is an `incident` artifact (`sport-itsm-architecture` §5.4, test 1 — "does it name a type from exactly one bounded context's domain?"), and every outbound adapter of a context lives in that context's own `type:infrastructure` library, never in `apps/api` (ADR-003, cross-context adapters only). Concretely: `libs/incident/infrastructure/src/lib/in-memory/in-memory-incident.repository.ts`, exported from `libs/incident/infrastructure/src/index.ts` beside `TypeOrmIncidentRepository` (`libs/incident/infrastructure/src/lib/typeorm-incident.repository.ts`). It reuses `IncidentEntity` (`incident.entity.ts`) and `IncidentMapper` (`incident.mapper.ts`) from the same library — `typeorm` stays a decorator-only dependency, never connected. **This is a production adapter of the prototype, not a test double**, held to the same review standard as `TypeOrmIncidentRepository`.

**Trimmed scope — the user's decision, recorded here.** An earlier pass of this ticket also built a shared repository-port contract suite (`ADR-015` consequence 7) exercised against both this adapter and `TypeOrmIncidentRepository`, to prove both honor the same *observable* port behavior. The Product Owner explicitly cut that suite from this delivery (slice 1b trimmed) — see **Out of scope** below. Without it, the adapter's own unit specs are the whole of this ticket's test surface, which is why the estimate is now 2h, not the 3h the suite used to push it to.

## Scope

- `InMemoryIncidentRepository implements IncidentRepositoryPort, IncidentReadRepositoryPort` in `libs/incident/infrastructure/src/lib/in-memory/in-memory-incident.repository.ts`:
  - `nextIdentity()`: a UUID v7 generated in-process, RFC 9562 §5.7, with **no new dependency** — 48-bit big-endian Unix-epoch milliseconds (`Date.now()`), version nibble `0111`, 12 bits of `rand_a` and 62 bits of `rand_b` from `node:crypto`'s `randomBytes`, variant bits `10`, rendered lowercase 8-4-4-4-12. Must satisfy `Identity.fromString()` (v7 only). Private to the `in-memory/` folder, not exported, not placed in `shared/util` (randomness and wall-clock time are not pure).
  - `nextReference()`: an in-process counter starting at `1`, incremented **before** the value is returned and never decremented (a handed-out value is consumed even if the following `save()` fails — "gaps acceptable, reuse never," `DATA-MODEL.md` §3.2). Rendered through the existing `IncidentReferencePolicy.format()`, which already throws `IncidentReferenceSequenceOutOfRangeError` past `9 999 999` — reuse it, do not reimplement the range check. Node's single-threaded event loop makes the increment atomic; no lock needed.
  - `save(incident)`: maps through the existing `IncidentMapper.toEntity()` and stores the resulting plain-object `IncidentEntity` snapshot (never attached to any `DataSource`), keyed by id, plus a `reference → id` index. Two structural rules the database would otherwise enforce, re-implemented here as typed infrastructure errors (neither is a `DomainError` — like a PostgreSQL constraint violation, each surfaces through `GlobalExceptionFilter`'s generic internal-error envelope, no new contract error code): **uniqueness** (a different id saved under an already-indexed reference is rejected) and **reference immutability** (a save for a known id whose reference differs from the stored one is rejected). A **capacity ceiling of 10 000** Incidents enforced on insert (unauthenticated public URL, unbounded map is a memory-exhaustion vector) — exceeding it is a third typed error.
  - `findById(id)` / `findByReference(ref)`: look up and return a **new** aggregate via `IncidentMapper.toDomain()`; `null` on absence, never a thrown "not found" — same contract `TypeOrmIncidentRepository` honors.
  - Provided in the default (singleton) Nest scope only — never request- or transient-scoped. (Binding it under `INCIDENT_REPOSITORY`/`INCIDENT_READ_REPOSITORY` is `T-C10-78`'s job, not this ticket's — this ticket only builds and exports the class.)
- Unit specs (`*.spec.ts`, co-located under `libs/incident/infrastructure/src/lib/in-memory/`), asserted **directly** against `InMemoryIncidentRepository` — no shared factory, no parameterization across adapters: v7 identities distinct and valid on repeated `nextIdentity()` calls; `nextReference()` yielding `INC` + seven digits, strictly increasing and never repeated within the instance, throwing `IncidentReferenceSequenceOutOfRangeError` past `9 999 999`; a full `save()`/`findById()`/`findByReference()` round-trip of every mapped field, returning a **new** aggregate instance each time; `null` on absence; a typed rejection when a second Incident is saved under an already-indexed reference, with the first left intact; a typed rejection when a known id is saved again with a different `reference` than the one already stored; the 10,000-Incident capacity ceiling enforced as a typed error on the 10,001st `save()`, contents otherwise unchanged; and the structural check that no `DataSource` is ever constructed or imported by this adapter.
- `TypeOrmIncidentRepository` is **not touched by this ticket** and stays covered exactly as today, by its own existing `integration` specs (`incident-reference-sequence.integration-spec.ts` and the rest) — no change to that target.
- Out of scope: binding either token to `InMemoryIncidentRepository` at the composition root, or anything that reads `PERSISTENCE_MODE` (`T-C10-78`); the config switch itself (`T-C10-75`); any change to `TypeOrmIncidentRepository`'s own behavior or its `integration`-target specs; **the shared repository-port contract suite** generalizing `IncidentRepositoryPort`/`IncidentReadRepositoryPort` conformance across both adapters (`ADR-015` consequence 7) — **deferred by the user's decision (slice 1b trimmed); revisit when ADR-015 is reverted.**

## Acceptance criteria

**Given** `InMemoryIncidentRepository.nextIdentity()` called repeatedly **When** the results are compared **Then** every value is a distinct, valid UUID v7 accepted by `Identity.fromString()`.

**Given** `InMemoryIncidentRepository.nextReference()` called repeatedly **When** the results are compared **Then** each is `INC` + seven digits, strictly increasing, never repeated within the same adapter instance, and the 10,000,000th call throws `IncidentReferenceSequenceOutOfRangeError`.

**Given** an Incident saved through `InMemoryIncidentRepository.save()` **When** it is reloaded via `findById()` and `findByReference()` **Then** every mapped field round-trips exactly, and each lookup returns a **new** aggregate instance the caller cannot use to mutate the stored snapshot.

**Given** a lookup by an id or reference with no matching Incident **When** `findById()`/`findByReference()` is called **Then** it resolves to `null`, never a thrown error.

**Given** a second Incident saved under a reference already indexed to a different id **When** `save()` is called **Then** it is rejected with a typed error and the first Incident's stored state is unchanged.

**Given** a known Incident id saved again with a different `reference` than the one already stored **When** `save()` is called **Then** it is rejected with a typed error and the persisted `reference` is unchanged.

**Given** 10,000 Incidents already stored **When** an 10,001st `save()` is attempted **Then** it is rejected with a typed capacity error and the store's contents are unchanged.
