# [C10] T-C10-77 · `InMemoryIncidentRepository` and the shared repository port contract suite

## Context

Foundation work with no user story behind it. Source: **ADR-015** (`docs/product/ARCHITECTURE.md` §10), decision 2 and consequence 7 — the second, non-durable adapter behind `IncidentRepositoryPort`/`IncidentReadRepositoryPort` that makes the Render prototype demonstrable with **no database on Render**, and the shared contract suite that proves both adapters honor the same *observable* port behavior.

**Placement, decided by ADR-015, not by this ticket.** An outbound adapter whose signatures name `Incident` is an `incident` artifact (`sport-itsm-architecture` §5.4, test 1 — "does it name a type from exactly one bounded context's domain?"), and every outbound adapter of a context lives in that context's own `type:infrastructure` library, never in `apps/api` (ADR-003, cross-context adapters only). Concretely: `libs/incident/infrastructure/src/lib/in-memory/in-memory-incident.repository.ts`, exported from `libs/incident/infrastructure/src/index.ts` beside `TypeOrmIncidentRepository` (`libs/incident/infrastructure/src/lib/typeorm-incident.repository.ts`). It reuses `IncidentEntity` (`incident.entity.ts`) and `IncidentMapper` (`incident.mapper.ts`) from the same library — `typeorm` stays a decorator-only dependency, never connected. **This is a production adapter of the prototype, not a test double**, held to the same review standard as `TypeOrmIncidentRepository`.

**Exceeds the 3h cap slightly by design — recorded rationale, not an oversight.** The adapter itself is roughly 1.5–2h; the remaining time is the shared port contract suite (below), which this ticket must build regardless, because ADR-015 consequence 7 ties the suite's existence to introducing the second adapter — no ticket after this one has a reason to build it, and splitting it into its own ticket would either duplicate the harness or leave `InMemoryIncidentRepository` unverified against the same contract `TypeOrmIncidentRepository` already implicitly satisfies. One reviewable unit: the adapter and the suite that proves it is a legitimate `IncidentRepositoryPort`/`IncidentReadRepositoryPort` implementer.

## Scope

- `InMemoryIncidentRepository implements IncidentRepositoryPort, IncidentReadRepositoryPort` in `libs/incident/infrastructure/src/lib/in-memory/in-memory-incident.repository.ts`:
  - `nextIdentity()`: a UUID v7 generated in-process, RFC 9562 §5.7, with **no new dependency** — 48-bit big-endian Unix-epoch milliseconds (`Date.now()`), version nibble `0111`, 12 bits of `rand_a` and 62 bits of `rand_b` from `node:crypto`'s `randomBytes`, variant bits `10`, rendered lowercase 8-4-4-4-12. Must satisfy `Identity.fromString()` (v7 only). Private to the `in-memory/` folder, not exported, not placed in `shared/util` (randomness and wall-clock time are not pure).
  - `nextReference()`: an in-process counter starting at `1`, incremented **before** the value is returned and never decremented (a handed-out value is consumed even if the following `save()` fails — "gaps acceptable, reuse never," `DATA-MODEL.md` §3.2). Rendered through the existing `IncidentReferencePolicy.format()`, which already throws `IncidentReferenceSequenceOutOfRangeError` past `9 999 999` — reuse it, do not reimplement the range check. Node's single-threaded event loop makes the increment atomic; no lock needed.
  - `save(incident)`: maps through the existing `IncidentMapper.toEntity()` and stores the resulting plain-object `IncidentEntity` snapshot (never attached to any `DataSource`), keyed by id, plus a `reference → id` index. Two structural rules the database would otherwise enforce, re-implemented here as typed infrastructure errors (neither is a `DomainError` — like a PostgreSQL constraint violation, each surfaces through `GlobalExceptionFilter`'s generic internal-error envelope, no new contract error code): **uniqueness** (a different id saved under an already-indexed reference is rejected) and **reference immutability** (a save for a known id whose reference differs from the stored one is rejected). A **capacity ceiling of 10 000** Incidents enforced on insert (unauthenticated public URL, unbounded map is a memory-exhaustion vector) — exceeding it is a third typed error.
  - `findById(id)` / `findByReference(ref)`: look up and return a **new** aggregate via `IncidentMapper.toDomain()`; `null` on absence, never a thrown "not found" — same contract `TypeOrmIncidentRepository` honors.
  - Provided in the default (singleton) Nest scope only — never request- or transient-scoped. (Binding it under `INCIDENT_REPOSITORY`/`INCIDENT_READ_REPOSITORY` is `T-C10-78`'s job, not this ticket's — this ticket only builds and exports the class.)
- The shared port contract suite: `libs/incident/infrastructure/src/testing/incident-repository.port-contract.ts` — test-only, **never exported from the library barrel**, excluded from `tsconfig.lib.json`. A single, parameterized Jest spec factory taking a `() => IncidentRepositoryPort & IncidentReadRepositoryPort` and asserting: v7 identities distinct on repeated calls; `INC` + seven digits, strictly increasing and never repeated within one adapter instance; save/`findById`/`findByReference` round-trips every mapped field; `null` on absence; a second Incident under an already-used reference is rejected with the first left intact; the persisted `reference` of an Incident never changes after an attempted save with a different one (the *observable* contract — the TypeORM adapter keeps it via `update: false`, the in-memory adapter by rejecting; the suite asserts the outcome, not the mechanism).
- Wire the suite against `InMemoryIncidentRepository` in `libs/incident/infrastructure`'s ordinary Nx `test` target (so it runs in CI's `verify` job with no database).
- Wire the **same** suite against the existing `TypeOrmIncidentRepository` inside its own `integration` target (`libs/incident/infrastructure/jest.integration.config.ts`, `*.integration-spec.ts` naming) — a thin spec that imports the shared factory and supplies a real, migrated-database-backed instance. This does not replace `incident-reference-sequence.integration-spec.ts` or any other existing PostgreSQL-only guarantee (sequence behavior under concurrent connections/rollback, the M18 trigger, `uq_incident_reference`) — those stay exactly where they are; this only adds the *shared* half of the coverage to the `integration` target, which previously had no reason to import a memory-mode artifact.
- Unit specs for the memory-specific rules the shared suite does not cover: counter start value, the capacity ceiling, the three typed errors, "no `DataSource` is ever constructed or imported by this adapter."
- Out of scope: binding either token to `InMemoryIncidentRepository` at the composition root, or anything that reads `PERSISTENCE_MODE` (`T-C10-78`); the config switch itself (`T-C10-75`); any change to `TypeOrmIncidentRepository`'s own behavior beyond being exercised by the shared suite.

## Acceptance criteria

**Given** `InMemoryIncidentRepository.nextIdentity()` called repeatedly **When** the results are compared **Then** every value is a distinct, valid UUID v7 accepted by `Identity.fromString()`.

**Given** `InMemoryIncidentRepository.nextReference()` called repeatedly **When** the results are compared **Then** each is `INC` + seven digits, strictly increasing, never repeated within the same adapter instance, and the 10,000,000th call throws `IncidentReferenceSequenceOutOfRangeError`.

**Given** an Incident saved through `InMemoryIncidentRepository.save()` **When** it is reloaded via `findById()` and `findByReference()` **Then** every mapped field round-trips exactly, and each lookup returns a **new** aggregate instance the caller cannot use to mutate the stored snapshot.

**Given** a lookup by an id or reference with no matching Incident **When** `findById()`/`findByReference()` is called **Then** it resolves to `null`, never a thrown error.

**Given** a second Incident saved under a reference already indexed to a different id **When** `save()` is called **Then** it is rejected with a typed error and the first Incident's stored state is unchanged.

**Given** a known Incident id saved again with a different `reference` than the one already stored **When** `save()` is called **Then** it is rejected with a typed error and the persisted `reference` is unchanged.

**Given** 10,000 Incidents already stored **When** an 10,001st `save()` is attempted **Then** it is rejected with a typed capacity error and the store's contents are unchanged.

**Given** the shared port contract suite **When** it runs against `InMemoryIncidentRepository` inside `libs/incident/infrastructure`'s ordinary `test` target **Then** it passes with no database of any kind reachable or required.

**Given** the same shared port contract suite **When** it runs against `TypeOrmIncidentRepository` inside the `integration` target (real, migrated PostgreSQL) **Then** it passes unchanged — the same assertions, a different adapter instance.

**Given** the codebase **When** it is grepped for an import of `libs/incident/infrastructure/src/testing/incident-repository.port-contract.ts` from outside a `*.spec.ts`/`*.integration-spec.ts` file **Then** there are no matches, and the library's `tsconfig.lib.json` excludes the `testing/` directory.

## Testing methodology (per story / feature)

Mechanical/adapter ticket, no user persona. Unit tests (`test` target, no DB) cover the adapter's own rules and the shared suite's in-memory run. A thin `*.integration-spec.ts` (real PostgreSQL, `integration` target) imports the same shared suite factory against `TypeOrmIncidentRepository` — this is the one piece of this ticket that touches the database-backed target, and it must not duplicate or weaken any existing PostgreSQL-only guarantee spec.

## Testing stack (for realistic recommendations)

**Jest 29.7** + `ts-jest`, `libs/incident/infrastructure`'s ordinary `test` target (memory-mode + adapter-specific unit specs, no DB) and its `integration` target (`libs/incident/infrastructure/jest.integration.config.ts`, ephemeral PostgreSQL 18.6 via `docker/docker-compose.e2e.yml`, exactly as `T-C1-06`'s existing round-trip spec already runs).

## Implementation handoff (split by level)

- **Unit** (`*.spec.ts`, co-located in `libs/incident/infrastructure/src/lib/in-memory/`) → `backend-engineer` — the adapter's own rules and the shared suite's in-memory run.
- **Integration** (`*.integration-spec.ts`, `libs/incident/infrastructure`) → `backend-engineer` — wiring the shared suite against `TypeOrmIncidentRepository`.

No E2E/acceptance-level work in this ticket; `testing-implementer` has no stake here.
