# [C10] T-C10-78 · `PersistenceModule.forMode()` — persistence selected once, at the composition root, as data

## Context

Foundation work with no user story behind it. Source: **ADR-015** (`docs/product/ARCHITECTURE.md` §10), decision 3 — "Selection happens once, at the composition root, as data — not as scattered conditionals." Depends on `T-C10-75` (`PersistenceMode` enum, `PERSISTENCE_MODE` on `EnvironmentVariables`) and `T-C10-77` (`InMemoryIncidentRepository`, exported from `libs/incident/infrastructure`) — both must exist before there is anything to select between.

Today, `apps/api/src/app/incident/incident.module.ts` binds `INCIDENT_REPOSITORY` → `TypeOrmIncidentRepository` unconditionally, and `apps/api/src/database/database.module.ts` (`DatabaseModule`) is imported once, globally, by `AppModule`. This ticket makes the binding a **function of `PERSISTENCE_MODE`**, resolved once, with no `if (PERSISTENCE_MODE === …)` anywhere in a controller, use case, adapter or spec helper — domain and application stay untouched, exactly as the hexagon is built to allow.

## Scope

- `apps/api/src/persistence/persistence.module.ts` — `PersistenceModule`, a `@Global()` dynamic module with a static `forMode(mode: PersistenceMode): DynamicModule` factory. `AppModule` calls it with `loadEnvironment().PERSISTENCE_MODE` — the same sanctioned, pre-DI environment read `AppModule` already performs for `TestEventDispatchModule` (`apps/api/src/app/app.module.ts`). **This becomes the only place in the codebase that reads `PERSISTENCE_MODE`.**
- `apps/api/src/app/incident/incident-persistence.bindings.ts` — exports `incidentPersistenceBindings: Record<PersistenceMode, Provider[]>`:
  - `postgres`: `{ provide: INCIDENT_REPOSITORY, useClass: TypeOrmIncidentRepository }`.
  - `memory`: `{ provide: INCIDENT_REPOSITORY, useFactory: () => new InMemoryIncidentRepository() }` (no constructor injection needed — the adapter takes no dependency).
  - Both modes: `{ provide: INCIDENT_READ_REPOSITORY, useExisting: INCIDENT_REPOSITORY }` — one adapter instance, two ports, in either mode, exactly as today.
  - `Record<PersistenceMode, Provider[]>` makes a context that forgets a mode a **compile error** — the exhaustiveness guarantee an `if` chain cannot give.
- `PersistenceModule.forMode(mode)` concatenates every context's bindings map it is given (today, just `incidentPersistenceBindings`) into its own `providers`/`exports`, and imports `DatabaseModule` **only** when `mode === PersistenceMode.Postgres` — `memory` mode never constructs a `DataSource`, never attempts a connection, and `apps/api`'s dependency graph proves `pg` is not loaded on that path.
- `apps/api/src/app/incident/incident.module.ts` **stops** binding `INCIDENT_REPOSITORY`/`INCIDENT_READ_REPOSITORY` itself — those two provider entries are removed from `IncidentModule` and now live only in `incidentPersistenceBindings`. `IncidentModule` keeps everything else unchanged: `INCIDENT_ACTOR_RESOLVER`, `SLA_POLICY`, `CLOCK`, `LogIncidentUseCase`'s and `GetIncidentByReferenceUseCase`'s `useFactory` bindings.
- `apps/api/src/app/app.module.ts` imports `PersistenceModule.forMode(loadEnvironment().PERSISTENCE_MODE)` once, globally, in place of its current unconditional `DatabaseModule` import.
- A boot-time spec proving the API starts in `memory` mode with **no** `POSTGRES_*` variable set and **no** `DataSource` provider resolvable/constructed — the memory-mode counterpart to the existing `postgres`-mode boot proof.
- Adapt `apps/api/src/app/incident/incident.module.spec.ts` (`T-C1-100` AC6 — the `useExisting` identity assertion): it currently composes `IncidentModule` alone plus `EventDispatchModule` and relies on `IncidentModule`'s own (now-removed) repository bindings. Update it to import `PersistenceModule.forMode(PersistenceMode.Memory)` alongside `IncidentModule` instead — this also **removes its implicit dependency on a real `DataSource`/PostgreSQL**, since the identity assertion (`INCIDENT_READ_REPOSITORY` resolves to the *same* instance as `INCIDENT_REPOSITORY`) holds equally in either mode and memory mode needs no live database to prove it.
- Adapt `apps/api/src/app/incident/log-incident.fixed-actor.spec.ts` (`T-C10-74` AC3) the same way — it composes `IncidentModule` + `EventDispatchModule` to exercise `LogIncidentUseCase` against the real production wiring; add `PersistenceModule.forMode(PersistenceMode.Memory)` to its `Test.createTestingModule` imports so `INCIDENT_REPOSITORY` resolves without a live connection.
- Out of scope: `apps/api/src/config/env.validation.ts`, `apps/api/src/data-source.ts` (`T-C10-75`); `InMemoryIncidentRepository` itself and the port contract suite (`T-C10-77`); the nginx proxy (`T-C10-79`); any change to `TypeOrmIncidentRepository`, `DatabaseModule`, or any other context's module (no other context has a persistence-mode split yet).

## Acceptance criteria

**Given** `PERSISTENCE_MODE=postgres` and valid `POSTGRES_*` values **When** the API boots **Then** `INCIDENT_REPOSITORY` resolves to a `TypeOrmIncidentRepository`, `DatabaseModule` is imported, and every existing `postgres`-mode behavior (intake, detail lookup) is unchanged.

**Given** `PERSISTENCE_MODE=memory` and no `POSTGRES_*` variable set **When** the API boots **Then** it starts successfully, `INCIDENT_REPOSITORY` resolves to an `InMemoryIncidentRepository`, `DatabaseModule` is never imported, and no `DataSource` provider is registered in the container.

**Given** the codebase **When** it is grepped for `PERSISTENCE_MODE` outside `apps/api/src/persistence/` **Then** the only other matches are `env.validation.ts`'s declaration and `data-source.ts`'s guard (both `T-C10-75`) — no controller, use case, adapter or module conditions on it.

**Given** `incidentPersistenceBindings` **When** a new `PersistenceMode` value is hypothetically added to the enum without updating this map **Then** the TypeScript build fails (the `Record<PersistenceMode, Provider[]>` exhaustiveness check), not a runtime `undefined`.

**Given** `apps/api/src/app/incident/incident.module.spec.ts` **When** it is re-run after this ticket **Then** it still proves `INCIDENT_READ_REPOSITORY` and `INCIDENT_REPOSITORY` resolve to the identical instance, now composed with `PersistenceModule.forMode(PersistenceMode.Memory)` and requiring no live database.

**Given** `apps/api/src/app/incident/log-incident.fixed-actor.spec.ts` **When** it is re-run after this ticket **Then** `LogIncidentUseCase` still authorizes and persists exactly as before, against the memory-mode binding, with no change to `LogIncidentUseCase`'s own file.

**Given** both intake (`POST /api/incidents`) and detail lookup (`GET /api/incidents/{reference}`) exercised against a `PERSISTENCE_MODE=memory` boot **When** an Incident is logged and then fetched by its returned reference **Then** the detail response matches exactly what was persisted, proving the wiring end to end without a database.

## Testing methodology (per story / feature)

Mechanical/composition-root ticket, no user persona of its own — the end-to-end proof in the last acceptance criterion above is the closest thing to a scenario, and it is what the ADR calls out as the point of the whole exercise (a person opens the web client, logs an Incident, sees it — this ticket is the backend half of that being true with no database). Covered by a new unit/integration-style Nest-testing spec (`@nestjs/testing`, no real HTTP, no real DB) plus the two adapted specs above.

## Testing stack (for realistic recommendations)

**Jest 29.7** + `@nestjs/testing`, `apps/api`'s ordinary `test` target — every spec this ticket adds or adapts runs with **no** PostgreSQL reachable, which is itself part of what the acceptance criteria prove.

## Implementation handoff (split by level)

Single-level change, no unit/E2E split: `backend-engineer` builds `PersistenceModule`, `incident-persistence.bindings.ts`, adapts `IncidentModule` and `AppModule`, and updates the two existing specs plus the new memory-mode boot spec, in one pass.

## Manual configuration checklist (Render / GitHub)

None specific to this ticket beyond the shared checklist already recorded in `T-C10-76`'s own ticket (Render service `sport-itsm-api`'s `PERSISTENCE_MODE=memory` environment variable) — this ticket is what makes that variable meaningful once it is set.
