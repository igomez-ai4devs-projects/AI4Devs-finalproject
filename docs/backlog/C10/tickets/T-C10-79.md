# [C10] T-C10-79 · nginx reverse-proxies `/api/` to the API service — same origin, no CORS

## Context

Foundation work with no user story behind it. Source: **ADR-015** (`docs/product/ARCHITECTURE.md` §10), decision 4. Today `docker/frontend/nginx.conf` is a static config with an SPA `try_files … /index.html` fallback and **no `location /api/`** — on stage, every API call falls through to that fallback and gets back `index.html` with a `200`, never the API's own JSON response. `libs/incident/data-access`'s `INCIDENT_API_BASE_URL` is already the **relative** path `'/api'` (development's `apps/web/proxy.conf.json` forwards it the same way) — ADR-015 decision 4 states plainly "no frontend change is required," so this ticket is entirely `docker/frontend/**` plus the one stage compose file.

**Independent of the backend persistence-mode work (`T-C10-75`/`77`/`78`).** This ticket can be built and locally verified in parallel with that chain — it only needs *some* API to proxy to, whichever mode it runs in. It becomes meaningful for the actual Render demo once both halves are merged.

## Scope

- Convert `docker/frontend/nginx.conf` into a **template** rendered at container start by the official `nginx` image's built-in `envsubst` step: place it at `/etc/nginx/templates/default.conf.template` (or the equivalent path for this image, e.g. `docker/frontend/nginx.conf.template`, `COPY`'d into that location by `docker/frontend/Dockerfile`) with `NGINX_ENVSUBST_OUTPUT_DIR` pointed at the file nginx actually loads. Keep every existing `location`/security-header/cache directive unchanged — this is an additive change, not a rewrite of the working SPA config.
- Add `location /api/ { proxy_pass <API_UPSTREAM_URL>; … }` — **no URI part** on `proxy_pass`, so `/api/incidents/…` reaches the API with its path unchanged, matching `apps/api`'s global prefix. `API_UPSTREAM_URL` is substituted from the environment at container start.
- Implementation constraints (ADR-015 decision 4, verbatim requirements this ticket must satisfy):
  - Resolve the upstream **at request time** — an nginx `resolver` directive plus a variable in `proxy_pass` — so nginx neither refuses to start on an unresolved host nor caches a stale address if the API's IP changes.
  - `proxy_ssl_server_name on` and `proxy_set_header Host <upstream host>` — Render routes by SNI/Host.
  - `proxy_connect_timeout`/`proxy_read_timeout` of **at least 60s**, so the first request after the API has spun down (Render free-tier idle behavior) waits instead of failing with a `504`.
  - `X-Forwarded-*` headers set on the proxied request.
  - The container **fails to start** when `API_UPSTREAM_URL` is unset — an explicit check in a `/docker-entrypoint.d/` script, not a silently broken literal left in the rendered config.
  - Every existing security header (`X-Frame-Options`, `X-Content-Type-Options`, `X-XSS-Protection`) stays intact and applies to the whole server block, including the new location.
- `docker/docker-compose.stage.yml` — add `API_UPSTREAM_URL=http://api:3300` to the `web` service's `environment:` block (the two services already share the `stage-network` bridge network and the `api` hostname resolves inside it).
- A local verification pass, run manually (not part of any automated CI job — the automated post-deploy smoke test is explicitly out of this delivery cut): `docker compose -f docker/docker-compose.stage.yml up`, then `curl -i http://localhost:4200/api/incidents/INC9999999` and confirm the response is the API's own `404` JSON error envelope (`GlobalExceptionFilter`'s shape), never `index.html`/`200`.
- Out of scope: any Render dashboard configuration (`API_UPSTREAM_URL`'s **production** value, `https://<api-service>.onrender.com`, is a manual step — see the checklist below, not a file this ticket edits); any change to `libs/incident/data-access` or `apps/web/proxy.conf.json` (ADR-015: none needed); CORS (deliberately not enabled, same-origin by construction); an automated post-deploy acceptance test against the deployed Render URL (cut from this delivery slice per the user's explicit scope reduction).

## Acceptance criteria

**Given** `docker/frontend/nginx.conf.template` (or equivalent) **When** it is inspected **Then** it declares a `resolver` directive and a `location /api/` block whose `proxy_pass` target is a variable populated from `API_UPSTREAM_URL`, with no URI segment appended.

**Given** the web container **When** it starts with `API_UPSTREAM_URL` unset **Then** it fails to start (non-zero exit / crash-loop), with a clear log message naming the missing variable — never a silently broken proxy.

**Given** the web container started with `API_UPSTREAM_URL` pointing at a reachable API **When** `GET /api/incidents/INC9999999` is requested through nginx **Then** the response is the API's own `404` JSON error envelope, not `index.html`, and not a nginx error page.

**Given** the same request **When** the proxied request is inspected on the API side **Then** it carries `X-Forwarded-For`/`X-Forwarded-Proto`/`X-Forwarded-Host` and a `Host` header naming the upstream, not the browser's original `Host`.

**Given** every existing static-asset and security-header rule in `nginx.conf` **When** the templated config is re-read after this ticket **Then** each rule is present and unchanged — this ticket is additive.

**Given** `docker/docker-compose.stage.yml` **When** it is inspected **Then** the `web` service's `environment:` block includes `API_UPSTREAM_URL=http://api:3300`.

**Given** a local `docker compose -f docker/docker-compose.stage.yml up` run with the persistence-mode work merged (`T-C10-75`/`77`/`78`) **When** a browser opens `http://localhost:4200/`, navigates to the intake form, submits it, and is redirected to the detail page **Then** the whole round trip succeeds through the single `localhost:4200` origin, with no CORS error and no direct browser call to the API's own port.
